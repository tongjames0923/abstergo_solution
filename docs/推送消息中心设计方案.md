# 推送消息中心设计方案（SIGNAL 信令 + 拉取 + 全链路日志）

| 项       | 内容                                                                                                                                                            |
|----------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 文档状态 | 设计定稿（已封版）                                                                                                                                              |
| 涉及模块 | `push-mod/push-api`（协议层小幅扩展）、`app`（业务主体）、`app-ui-vue`（前端）                                                                                  |
| 核心思路 | 消息先落库（fan-out 接收人），SSE/WS 仅推送轻量 `SIGNAL` 信令；前端收到信令后调用分页拉取接口获取完整消息；已读等状态由操作日志派生；操作日志同时承担全链路审计 |
| 成功语义 | **入库即投递成功**；是否抵达前端由拉取接口闭环，不依赖信令送达                                                                                                  |

---

## 0. 背景与设计决策

### 0.1 背景

现有推送链路（`POST /private/push/send` → `IPushEndpoint.publish` → DATA 帧全量载荷 → 前端直接渲染）存在三个能力缺口：

1. 消息不持久化：内存消息源（容量 10000，重启即清），离线/错过的消息不可恢复；
2. 无接收人模型：topic 广播语义，无法回答"谁发的、发给谁、谁读了、谁没读"；
3. 前端纯被动接收：无历史消息、无未读管理、无消息中心。

### 0.2 核心设计决策

| #   | 决策                                             | 说明                                                                                                      |
|-----|--------------------------------------------------|-----------------------------------------------------------------------------------------------------------|
| D1  | 信令落在 **FrameType** 上，不落在 payload        | 新增 `FrameTypeEnum.SIGNAL`；DATA 帧保持"纯业务数据"语义不变                                              |
| D2  | **旧链路完整保留**                               | `/private/push/send`、`PushNotifyMessage` 契约、全量 DATA 推送原样不动，框架仍可完全依靠 SSE/WS 运行      |
| D3  | 消息源（信令）**继续用内存实现**                 | 信令丢失无害（DB 是真相来源），`IPushMessageStore` 契约零改动                                             |
| D4  | 接收人解析收敛到**应用层 SPI**                   | `INotifyReceiverResolver` 由业务实现，推送架构不关心"该谁收"                                              |
| D5  | **fan-out 落库**接收人                           | `push_message_receiver` 每接收人一行                                                                      |
| D6  | 拉取接口是**分页消息列表**（到达序倒序，含已读） | 未读过滤是列表筛选条件；单页默认 20 条；游标 = 接收行自增 id                                              |
| D7  | 信令 payload **留空**                            | 信令只表达"该频道有新消息"；不携带消息标识                                                                |
| D8  | **勿扰不在本设计范围**                           | 勿扰 = 前端不订阅 signal 频道（纯前端行为）；是否落库由 SPI 决定                                          |
| D9  | 清理任务**不在本期范围**                         | 业务方自建定时任务；Service 预留物理清理内部方法供其调用                                                  |
| D10 | 不引入 MQ                                        | 消息源表即队列（Outbox 思想），当前量级（约 5000 条/天）无必要                                            |
| D11 | **无消息标识冗余列**                             | `push_message.id` 即业务消息标识，不设 message_key 等第二标识                                             |
| D12 | **读状态由操作日志派生**                         | 不设 read_time/read_flag 列；`已读 = 存在 READ 操作记录`；操作日志同时是全链路审计（SEND/READ/CLICK/...） |
| D13 | **数据库层零业务约束**                           | 无外键、无唯一键、无 CHECK、无 DEFAULT、无组合主键；业务完整性 100% 在应用层；索引仅为查询加速            |

### 0.3 设计演进决策记录（ADR）

> 以下为设计推演过程中被否决的方案及否决理由，固化下来防止绕回。

| 被否决方案                                                       | 否决理由                                                                                                                                                                                                                                                                |
|------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 独立消息状态表（稀疏存储已读状态）                               | 稀疏 upsert 依赖唯一键判定冲突，与 D13（无唯一键）直接冲突：并发已读会产生重复状态行且 DB 无法拦截；且读状态与接收关系是 1:1，拆表断裂读写局部性、未读计数间接化、清理一致性复杂化。**操作日志表（append-only）达成同样的状态外置目标且天然幂等**——重复日志行不破坏语义 |
| message_key 独立业务标识（含时间前缀键）                         | 主表自增 id 已承担唯一标识；第二标识列无唯一约束兜底、无跨库引用、无幂等职责，纯冗余。时间前缀键的唯一用途（清理定界）由 `create_time` 索引替代                                                                                                                         |
| 复合主键 `(receiver, message_id)`                                | 业务逻辑不入库原则；代理主键 + 普通二级索引即可覆盖查询路径                                                                                                                                                                                                             |
| 行格式极致压缩（BINARY 键、NULL 稀疏技巧、单列索引隐含排序依赖） | 目标规模（28 天约 25MB、百万行级）下所有物理优化收益不可测量；真正决定查询速度的是访问路径（索引对齐、游标分页、JOIN 键两侧索引化），这些已全部具备。行宽优化重新入场的触发条件：热数据集超出 Buffer Pool 且分区/归档策略已用尽                                         |
| 为推送链路引入 MQ                                                | 信令丢失无害 + DB 落库即成功语义下，MQ 的可靠性投递无增量价值；量级远未到削峰需求                                                                                                                                                                                       |

### 0.4 非目标

- 不做消息撤回、修改；
- 不做多端已读同步的额外设计（已读由日志派生，同账号天然共享）；
- 不做保留期外的历史归档/聚合报表；
- 不做信令的可靠投递补偿（由前端建连/重连后主动拉取兜底）；
- 不做发送幂等键（同一业务动作重复调用 = 两条消息，业务侧以自有业务键查重）。

## 1. 数据流转

### 1.1 数据分类与来源

| 数据         | 来源                                             | 载体                                       | 介质                                    | 写模式                   | 生命周期                 |
|--------------|--------------------------------------------------|--------------------------------------------|-----------------------------------------|--------------------------|--------------------------|
| 消息本体     | `POST /private/push/notify` / 程序化调用 Service | `PushNotifySendForm` → `PushMessageEntity` | DB 表 `push_message`                    | INSERT 后不可变          | 保留期内外部清理         |
| 投递关系     | 发送事务内 fan-out 生成                          | `PushMessageReceiverEntity`                | DB 表 `push_message_receiver`           | 纯 INSERT                | 同主表                   |
| 生命周期行为 | 发送（SEND）、阅读（READ）、点击（CLICK）等      | `PushMessageOperationLogEntity`            | DB 表 `push_message_operation_log`      | 纯 INSERT（append-only） | 可独立于关系表设置保留期 |
| 投递信令     | 发送事务提交后逐接收人发布                       | `PushFrame(type=SIGNAL)`                   | 内存 `InMemoryPushMessageStore`（现有） | 投递一次即消费           | 短命                     |
| 投递留痕     | 分发器逐会话投递动作                             | `DeliveryRecord`                           | 内存（现有）                            | ——                       | 纯诊断信息，可随时丢弃   |

三张业务表 **全 append-only：整个消息中心 schema 无任何 UPDATE 路径**。

### 1.2 数据模型

#### 1.2.1 消息主表 `push_message`

```sql
CREATE TABLE push_message
(
    id          BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键（即业务消息标识）',
    topic       VARCHAR(128) NOT NULL COMMENT '业务主题',
    msg_type    VARCHAR(32)  NOT NULL COMMENT '消息类型（可字典驱动扩展）',
    title       VARCHAR(255) COMMENT '标题',
    content     TEXT COMMENT '正文',
    priority    VARCHAR(16)  NOT NULL COMMENT '优先级（Service 缺省填充，无 DB 默认值）',
    sender      VARCHAR(64) COMMENT '发送者标识（展示用，审计权威见操作日志）',
    url         VARCHAR(512) COMMENT '点击跳转地址',
    ext_info    TEXT COMMENT '扩展信息（JSON，业务自定义字段，避免频繁 DDL）',
    create_time DATETIME     NOT NULL COMMENT '创建时间',
    update_time DATETIME COMMENT '更新时间',
    PRIMARY KEY (id),
    KEY idx_create_time (create_time)
) COMMENT '推送业务消息主表';
```

#### 1.2.2 接收人表 `push_message_receiver`

```sql
CREATE TABLE push_message_receiver
(
    id          BIGINT   NOT NULL AUTO_INCREMENT COMMENT '主键（兼游标分页排序键，自增即到达序）',
    message_id  BIGINT   NOT NULL COMMENT '消息ID（push_message.id）',
    receiver    BIGINT   NOT NULL COMMENT '接收用户ID',
    create_time DATETIME NOT NULL COMMENT '创建时间',
    update_time DATETIME COMMENT '更新时间',
    PRIMARY KEY (id),
    KEY idx_receiver (receiver),
    KEY idx_create_time (create_time)
) COMMENT '推送消息接收人表（纯投递关系，append-only）';
```

#### 1.2.3 操作日志表 `push_message_operation_log`（全链路消息日志）

```sql
CREATE TABLE push_message_operation_log
(
    id          BIGINT      NOT NULL AUTO_INCREMENT COMMENT '主键',
    message_id  BIGINT      NOT NULL COMMENT '消息ID',
    operator    BIGINT COMMENT '操作人（系统/服务发起时可空，身份进 ext_info）',
    op_type     VARCHAR(32) NOT NULL COMMENT '操作类型：SEND/READ/CLICK/...（可字典驱动扩展）',
    op_source   VARCHAR(32) COMMENT '来源通道：http/rpc/job/system',
    op_time     DATETIME    NOT NULL COMMENT '操作时间',
    ext_info    TEXT COMMENT '上下文扩展（服务名、调用方标识、点击位置等）',
    create_time DATETIME    NOT NULL COMMENT '创建时间',
    update_time DATETIME COMMENT '更新时间',
    PRIMARY KEY (id),
    KEY idx_operator_msg (operator, message_id),
    KEY idx_message (message_id),
    KEY idx_op_time (op_time)
) COMMENT '消息全链路操作日志（append-only，已读由存在READ记录派生）';
```

模型说明：

- **三表全单列主键、零唯一键、零外键、零组合索引**；四个二级索引全部为查询加速（主表时间检索/清理、关系表分页与未读统计、日志表已读探查与全链路聚合、日志清理）；
- **`sender` 列与 SEND 日志行并存**：主表行是"消息本体"（sender 用于列表展示），日志行是"行为审计"（operator + op_source
  权威记录，覆盖 RPC/Job 等无请求日志的通道）；
- **投递关系不复制进日志**：日志记录"行为事件"，关系表记录"关系事实"，全链路由三源拼图（见 1.3.2）；
- **重复日志行无害**：append-only 下同一消息多次 READ 记录语义不变，未读计数用 `COUNT(DISTINCT message_id)` 抵消；
- **CLICK 是否算已读是业务规则**：默认点击同时补记一条 READ（Service 封装，可调整）。

#### 1.2.4 数据转换规则

| 转换                                                      | 发生位置                                                           | 规则                                                                                               |
|-----------------------------------------------------------|--------------------------------------------------------------------|----------------------------------------------------------------------------------------------------|
| `PushNotifySendForm` → `PushMessageEntity`                | Service 发送事务内                                                 | id 由 DB 回填；`msgType`/`priority` 校验；`topic` 缺省 `global.broadcast`；`@AutoSetDate` 填充时间 |
| Entity + SPI 解析结果 → `List<PushMessageReceiverEntity>` | Service 发送事务内                                                 | receivers 去重（应用层保证，DB 无唯一约束兜底）；批量 insert                                       |
| Entity + 发起上下文 → SEND 日志行                         | Service 发送事务内                                                 | `operator`=登录用户（无则空 + `ext_info` 声明身份）；`op_source`=调用通道；`op_time`=now           |
| 阅读/点击动作 → READ/CLICK 日志行                         | Service                                                            | `operator`=当前登录用户；`op_time`=now                                                             |
| 三表 → `PushNotifyMessageVO`                              | Service 拉取                                                       | 主表 + 接收行关联，日志表批量探查已读标注（见 1.4）                                                |
| Entity → SIGNAL 帧                                        | `JsonPushCodec.encodeMessage`（按 `PushMessage.frameType=SIGNAL`） | `type=SIGNAL`、`topic=用户频道`、`messageId=帧级UUID`、`payload=null`；**消息内容不进信令**        |

### 1.3 数据流转全景图

#### 1.3.1 发送侧

```
业务方（HTTP 或 RPC/Job 程序化调用）
  │ POST /private/push/notify {msgType,title,content,...}   ← 不传接收人
  ▼
PrivatePushMessageController（HTTP 接入，参数组装）
  ▼
IPushNotifyService.send(form)                     [@Transactional]
  ├─ ① 契约校验（AssertUtil + i18n）
  ├─ ② INSERT push_message（id 回填）              ← 消息本体落库
  ├─ ③ SPI: INotifyReceiverResolver.resolve(form) → receivers
  ├─ ④ 去重 → 批量 INSERT push_message_receiver    ← fan-out 落库
  ├─ ⑤ INSERT push_message_operation_log(SEND)     ← 发送行为留痕（同一事务，链路起点）
  ▼ 事务提交（信令发布在事务外）
  └─ ⑥ 逐接收人 pushEndpoint.publishSignal(tbs.push.channel.{receiver}, null)
         → PushMessage{frameType=SIGNAL} → 内存消息源 enqueue
         → AbstractPushDispatcher.fetchPending（取出即占用）
         → TopicRouteCoordinator 按 topic 匹配订阅会话
         → JsonPushCodec.encodeMessage（SIGNAL 帧）→ 会话下行
              ├─ 在线且订阅频道 → SIGNAL 帧送达前端
              └─ 否则 → NO_SUBSCRIBER 留痕（内存），无补偿
```

#### 1.3.2 拉取侧与全链路

```
【拉取】
前端收到 SSE 'signal' 事件 / WS SIGNAL 帧
  → debounce 300ms → GET /private/push/messages?cursor=&limit=20（第一页，到达序倒序，含已读）
  → 按 messageId 合并去重 → 渲染 → 更新未读角标
前端建连/重连成功（hello 帧后）→ 主动拉第一页（兜底离线/丢信令）
用户阅读/点击 → POST 处理接口 → INSERT 操作日志（READ/CLICK）

【全链路拼图】（Service 组装，按 message_id）
  SEND 日志行（谁、哪条通道、何时发）
  + receiver 行集（发给了谁）
  + READ/CLICK 日志行集（谁处理了、何时、来源）
```

### 1.4 存储访问路径

| 访问场景                 | 索引                                       | 路径                                                                                                                           |
|--------------------------|--------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------|
| 消息列表分页             | `receiver.idx_receiver`                    | `WHERE receiver=? AND id<? ORDER BY id DESC LIMIT ?`（单用户内自增序=到达序）                                                  |
| 列表已读标注（每页一次） | `log.idx_operator_msg`                     | `SELECT message_id, MIN(op_time) FROM log WHERE operator=? AND message_id IN(页内20个) AND op_type='READ' GROUP BY message_id` |
| 未读计数                 | 两表                                       | `COUNT(receiver行) − COUNT(DISTINCT message_id WHERE operator=? AND op_type='READ')`；单用户行数受保留期×日增量约束            |
| 记录已读/点击            | ——                                         | `INSERT log(...)`（append-only，重复提交多一行，语义不变）                                                                     |
| 全链路审计（按消息）     | `log.idx_message`                          | `WHERE message_id=?` 取全部事件；投递关系走 `receiver` 全扫描（低频管理端操作，增长路径见 1.5）                                |
| 清理（业务方自建）       | 各表 `idx_create_time` / `log.idx_op_time` | 按时间分批 `LIMIT` 删除                                                                                                        |

### 1.5 一致性规则与增长路径

**一致性规则**：

1. **先落库后发信令**：信令发布在事务提交之后；信令只会"晚到/丢失"，不会"提前"；
2. **入库即成功**：返回 `messageId` 即代表消息、接收关系、SEND 日志已持久化；信令送达不作判据；
3. **信令可重复、可丢失**：前端按 messageId 合并 + 已读状态由日志派生，重复拉取与信令重复均幂等；
4. **操作日志天然幂等语义**：append-only，重复记录不破坏派生规则；所有派生查询用 DISTINCT/EXISTS 语义消化重复；
5. **发送事务原子**：主表 + fan-out + SEND 日志同一事务，全成全败。

**增长路径**（触发才做，不预做）：

- 管理端"按消息查投递明细"频率上升 → `receiver` 加 `KEY(message_id)`；
- 数据量至千万级 → 按月 RANGE 分区 + 归档策略；
- 热数据集超出 Buffer Pool → 先调内存配置，再谈行宽。

## 2. 业务流转

### 2.1 角色与职责

| 角色             | 位置                                    | 职责                                                                                                | 明确不负责                  |
|------------------|-----------------------------------------|-----------------------------------------------------------------------------------------------------|-----------------------------|
| 业务发送方       | 业务代码 / HTTP 调用方                  | 构造 `PushNotifySendForm` 调用发送接口                                                              | 接收人解析、fan-out、发信令 |
| 接收人解析 SPI   | app 模块 `INotifyReceiverResolver` 实现 | 唯一决策"消息该让谁收到"（部门/角色/全员/指定人/排除均可）                                          | 落库、发信令                |
| 推送业务 Service | app 模块 `PushNotifyServiceImpl`        | 契约校验、事务（落库+fan-out+SEND日志）、提交后发信令、拉取/已读派生/计数、全链路组装、预留清理方法 | HTTP 感知                   |
| 协议层           | push-api（小幅扩展）                    | SIGNAL 帧定义、信令入源与分发编排、订阅匹配                                                         | 消息内容持久化、接收人语义  |
| 传输适配层       | sse-impl / websocket-impl               | SIGNAL 帧下行承载（零改动）                                                                         | 任何业务逻辑                |
| 前端             | app-ui-vue `src/push/`                  | 订阅频道、信令监听（debounce）、拉取渲染、操作回传、未读角标                                        | 勿扰以外的业务规则          |
| 外部清理任务     | 业务方自建                              | 保留期外物理删除三表                                                                                | 调用 Service 预留清理方法   |

### 2.2 发送流程

```
触发条件：POST /private/push/notify 或程序化调用 IPushNotifyService.send

① Controller 接入（仅参数组装）→ Service.send(form)
② 事务开启
   ├─ 契约校验：msgType 必填；priority 可选白名单（缺省 normal，Service 填充）；
   │            topic 可选（缺省 global.broadcast，≤128 字符）
   ├─ INSERT push_message（id 回填）
   ├─ SPI 解析 receivers → 去重 → 批量 INSERT push_message_receiver
   ├─ INSERT SEND 操作日志（operator=登录用户/空，op_source=http/rpc/job/...）
③ 事务提交
④ 逐接收人 publishSignal：topic=tbs.push.channel.{receiver}，payload=null
⑤ 响应 {messageId, topic, receiverCount}
```

关键约束：

- **信令发布在事务提交后**（事务内禁止不可回滚操作）；
- SPI 抛异常视为 **发送失败**，事务整体回滚（含 SEND 日志）；
- receivers 为空是 **合法状态**：消息落主表 + SEND 日志，无 fan-out、无信令，`receiverCount=0`；
- 发送无幂等键：重复调用产生两条消息，业务侧自查重（D-非目标）。

### 2.3 接收、拉取与处理流程

```
触发条件 A：收到 SIGNAL（在线实时）
  → debounce 300ms → 拉第一页 → 按 messageId 合并去重 → 渲染 + 角标

触发条件 B：建连/重连成功（hello 帧后）
  → 主动拉第一页（兜底：离线期间消息、丢失信令）

触发条件 C：用户阅读/点击
  → INSERT 操作日志（READ/CLICK，operator=当前用户）
  → 已读状态由日志派生（无需回写任何状态列）
  → 前端本地更新角标

订阅管理（前端自主）：
  建连后 SUBSCRIBE tbs.push.channel.{当前用户}
  勾扰 → UNSUBSCRIBE / 不订阅：仅停信令，消息照常落库可拉取
```

### 2.4 状态派生（无状态列）

```
已读（派生规则，Service 封装）：
  已读 ⇔ 存在操作日志 (operator=该用户, message_id=该消息, op_type='READ')
  readTime ⇔ 该消息首条 READ 记录的 op_time
  重复 READ 记录：语义不变，计数用 DISTINCT 消化

未读（派生规则）：
  未读 ⇔ 存在接收关系 且 不存在 READ 记录

业务规则示例（CLICK 语义）：
  默认：点击同时补记一条 READ（点击即视为已读）
  可调整：由 Service 单点修改，不影响表结构
```

### 2.5 异常分支处理

| #   | 异常场景                     | 处理                                                                                       | 用户感知                       |
|-----|------------------------------|--------------------------------------------------------------------------------------------|--------------------------------|
| E1  | 契约校验失败                 | `AssertUtil` 抛用户输入错误，事务未开启                                                    | i18n 错误响应                  |
| E2  | SPI 解析抛异常               | 发送失败，事务整体回滚（主表+fan-out+SEND日志）                                            | 调用方收到错误，消息不存在     |
| E3  | SPI 返回空列表               | 合法：主表+SEND日志落库，无 fan-out、无信令                                                | `receiverCount=0`              |
| E4  | 事务提交后、发信令前进程崩溃 | 数据已完整落库，收不到实时信令 → 前端建连/重连拉取兜底                                     | 消息延迟可见                   |
| E5  | 信令投递失败（会话死亡）     | 记 `FAILED` 留痕（内存），不重试                                                           | 本次未实时收到，重连后拉取补齐 |
| E6  | 接收人离线/未订阅/勿扰       | `NO_SUBSCRIBER` 留痕，无补偿                                                               | 消息在下次拉取可见             |
| E7  | 清理任务非原子导致跨表孤儿行 | 列表 JOIN 不到主表行则跳过；清理建议顺序：先主表取过期 id 批次 → 删两从表批次 → 删主表批次 | 无感知                         |
| E8  | 操作日志重复（并发阅读）     | append-only 语义天然容错，派生查询 DISTINCT 消化                                           | 无感知                         |
| E9  | 信令风暴                     | 前端 debounce 合并；内存源容量（10000）满淘汰最早，对应消息仍可拉取                        | 无感知                         |
| E10 | 未读超单页 20 条             | 游标继续翻页；信令刷新第一页不影响旧页浏览                                                 | 正常分页体验                   |
| E11 | 重复发送（无幂等键）         | 产生两条独立消息，各自完整链路                                                             | 由业务侧自查重（非目标范围）   |

### 2.6 与旧链路共存

| 维度        | 旧链路（全量推送）                   | 新链路（信令+拉取）                                |
|-------------|--------------------------------------|----------------------------------------------------|
| 发送接口    | `POST /private/push/send`（保留）    | `POST /private/push/notify`（新增）                |
| 载荷契约    | `PushNotifyMessage`（调用方自带 id） | `PushNotifySendForm`（服务端生成 id）              |
| 帧类型      | DATA（payload=完整业务 JSON）        | SIGNAL（payload 空）；DATA 语义不变                |
| topic 语义  | 业务主题                             | 用户频道 `tbs.push.channel.{userId}`，命名空间隔离 |
| 前端处理    | payload 直接渲染（现有）             | 信令触发拉取（新增）                               |
| 持久化/审计 | 无                                   | 三表全链路                                         |

两链路共享协议层/传输层/会话体系，互不感知；同一前端可同时订阅两类 topic。

### 4.3 SPI 接口契约 `INotifyReceiverResolver`

```java
/**
 * 推送通知接收人解析 SPI
 * <p>
 * "消息应该让谁收到"的唯一决策点。解析结果直接决定 fan-out 落库范围与信令发布范围；
 * 抛出异常视为发送失败（事务回滚），返回空列表视为合法的"无接收人"。
 * </p>
 */
public interface INotifyReceiverResolver {

    /**
     * 是否支持处理该消息（多实现按命中链式分派）
     *
     * @param form 发送表单
     * @return true 表示由本实现解析
     */
    boolean supports(PushNotifySendForm form);

    /**
     * 解析接收人列表（Service 侧兜底去重）
     *
     * @param form 发送表单
     * @return 接收用户标识列表，可为空列表
     */
    List<Long> resolveReceivers(PushNotifySendForm form);
}
```

默认实现 `DefaultNotifyReceiverResolver`：`supports` 恒 true、返回空列表，`@ConditionalOnMissingBean`
注册。勿扰语义由实现方自行决定（从返回列表排除 = 不落库不拉取；不排除 = 落库静默）。

### 4.4 协议层接口改动

```java
/**
 * 发布信令消息
 * <p>入源一条 frameType=SIGNAL 的消息并触发即时分发；payload 允许为空。
 * 信令送达与否不影响业务成功语义（入库即成功）。</p>
 *
 * @param topic   目标频道主题（如 tbs.push.channel.{userId}）
 * @param payload 信令载荷文本，允许为 null
 * @return 帧消息唯一标识
 */
String publishSignal(String topic, String payload);
```

SIGNAL 帧线上格式（SSE 事件）：

```
event: signal
data: {"version":1,"type":"SIGNAL","messageId":"e3b0c442...","topic":"tbs.push.channel.1001","timestamp":1758431400000,"payload":null}
```

### 4.7 调用约束

1. 全部接口位于 `/private/**`，须携带有效登录令牌；当前用户统一经 `AuthUtil.getInstance().getCurrentUser()` 获取；
2. 发送接口无幂等键：重复提交产生重复消息，业务侧自查重；
3. `limit` 上限 100、已读回传单次上限 100；
4. 信令 topic 命名空间 `tbs.push.channel.` 保留给本机制，业务 topic 不得占用该前缀；
5. 分页必须使用游标（cursor），不支持 offset；
6. 操作日志表是 **消息域日志**：`op_type` 取值限定消息生命周期事件（与 message_id 强相关），禁止挪作通用审计；
7. 旧接口 `POST /private/push/send` 语义与行为不变，新旧调用方可并存。
