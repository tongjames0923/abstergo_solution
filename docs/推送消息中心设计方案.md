# 推送消息中心设计方案（SIGNAL 信令 + 拉取 + 全链路日志）

| 项       | 内容 |
|----------|------|
| 文档状态 | 与当前代码对齐（2026-10 复核） |
| 一句话   | 消息先落库（fan-out 接收人），长连接只推空载荷 `SIGNAL` 信令；客户端收到信令后调分页拉取接口取正文；读状态由操作日志派生；操作日志兼作全链路审计 |
| 成功语义 | **入库即投递成功**；是否抵达前端由拉取接口闭环，不依赖信令送达 |
| 代码落点 | 协议层 `push-mod/push-api`；业务契约 `system/system-api`；业务实现 `system/default-system-impl`；实体 `shared/shared-pojo`；Mapper `shared/shared-api`；HTTP 薄壳与 SSE 端点 `app`；前端 `app-ui-vue/src/push` |

> 说明：本文所有类名、包名、接口路径、常量、配置键均取自当前代码仓库实测；与设计初稿（旧版）不一致处见 §9「与旧稿的差异」。

## 0. 从 0 到 1 的构建设计思路

本章不讲结论，讲**推导**：从一个已有的"管道"出发，逐问收敛到当前形态。每一问都列出候选方案与选择理由，帮助读者判断"哪些设计是必然、哪些是权衡"。

### 0.1 起点：已经有一根"管道"

在消息中心之前，`push-mod` 已提供一条**可复用的长连接推送管道**：

- 协议层（`push-api`）定义帧（`PushMessage`）、编解码（`IPushCodec`）、凭证（`PushCredential`）、消息源（`IPushMessageStore`）、分发器（`AbstractPushDispatcher`）、门面（`IPushEndpoint.publish`）；
- 传输层两套实现：`sse-impl`（SSE 下行 + HTTP POST 上行）与 `websocket-impl`；
- 旧用法：`publish(topic, payload)` → 编码为 **DATA 帧**全量下发 → 前端拿到载荷直接渲染。

这根管道能"把一条消息瞬间广播给订阅了某 topic 的在线连接"，但它天生只解决"**在线、即时、广播**"三件事。

### 0.2 缺口：消息中心需要的，恰恰是管道没有的

要做"站内消息中心/通知中心"，需要回答一组问题，而旧 DATA 链路一个都答不了：

1. 用户**离线**时发的消息，上线后还在吗？（旧：内存源重启即清，丢了）
2. 这条消息**发给了谁、谁读了、谁没读**？（旧：topic 广播，无接收人模型）
3. 有没有**历史列表、未读角标、翻页**？（旧：纯被动接收，无）
4. 消息量很大时，能不能**不靠长连接硬扛全量载荷**？

三个结构性缺口：**不持久化、无接收人、纯被动**。

### 0.3 逐问推导（Q → 候选 → 选择）

| # | 问题 | 主要候选 | 本设计的选择 | 理由 |
|---|------|----------|--------------|------|
| Q1 | 消息存哪 | 只走内存源 / 落 DB | **落 DB（append-only）** | 离线可恢复、可审计、可分页；内存源降级为"信令的临时载体" |
| Q2 | 长连接推什么 | 推全量 DATA / 推空信令 + 拉 | **推 `SIGNAL` 空信令 + 拉取** | 信令只表达"该频道有新消息"，载荷留空；正文经鉴权的分页接口拉取，天然获得历史/未读/翻页，且单条大消息不占用广播通道 |
| Q3 | 信令靠什么区分 | 加 payload 字段 / 加帧类型 | **加帧类型 `FrameTypeEnum.SIGNAL`** | 帧类型是协议级语义，不污染 DATA 载荷语义；DATA 保持"纯业务数据"不变 |
| Q4 | 发给谁（接收人） | 架构内置 / 应用层 SPI | **应用层 SPI `INotifyReceiverResolver`** | "谁该收"是业务问题（部门/角色/用户名…），推送架构不关心；业务实现 Bean 即覆盖默认 |
| Q5 | 接收人怎么存 | 消息表内 JSON / 独立关系表 fan-out | **独立 `push_message_receiver` 每接收人一行** | 才能按接收人索引查列表、算未读、游标翻页 |
| Q6 | 读状态怎么存 | 状态列 / 唯一键 upsert 状态表 / 操作日志派生 | **操作日志派生（存在 READ 记录即已读）** | 见 Q8；避免状态表引入唯一键与并发 upsert |
| Q7 | 翻页方式 | offset / 游标 | **游标 = 接收行自增 id** | 到达序即 id 序，`id < cursor ORDER BY id DESC LIMIT n+1` 判 hasMore，深翻页稳定不漂 |
| Q8 | DB 要不要业务约束 | 外键/唯一键/CHECK | **零业务约束**（无外键/唯一键/组合主键） | 业务完整性 100% 在应用层写入路径保证；索引**仅为查询加速**（含日志表一个复合索引） |
| Q9 | 要不要引入 MQ | 落库即队列 / MQ 削峰 | **不引入 MQ** | 信令丢失无害（DB 是真相）、落库即成功语义下 MQ 无增量价值；量级未到削峰需求 |
| Q10 | 发送前能否干预消息 | 无扩展点 / 拦截器链 | **`IPushMessageInterceptor` 链** | 业务可在发送前脱敏/改写/富化表单（如统一签名、注入路由），命中才生效 |

### 0.4 决策快照（D1–D15）

| # | 决策 | 说明 |
|---|------|------|
| D1 | 信令落在**帧类型**上 | `FrameTypeEnum.SIGNAL`；DATA 语义不变 |
| D2 | 旧 DATA 链路**保留为编程能力** | `IPushEndpoint.publish` 仍在，框架仍可纯 SSE/WS 运行；但**旧 `/private/push/send` HTTP 端点已从当前控制器移除**（详见 §9） |
| D3 | 信令**继续用内存源** | 信令丢失无害（DB 为真相），`IPushMessageStore` 契约零改动 |
| D4 | 接收人解析收敛到**应用层 SPI** | `INotifyReceiverResolver`，默认 `TopicPrefixNotifyReceiverResolver`（按 topic 前缀查用户表） |
| D5 | **fan-out 落库**接收人 | `push_message_receiver` 每接收人一行 |
| D6 | 拉取接口是**分页消息列表** | 到达序倒序、含已读；未读为筛选条件；单页默认 20；游标 = 接收行 id |
| D7 | 信令 payload **留空** | 只表达"新消息"，不携带消息标识 |
| D8 | **勿扰不在本设计范围** | 前端不订阅 signal 频道即可；是否落库由 SPI 决定 |
| D9 | 清理**不在本期内置调度** | Service 提供 `cleanupBefore(Date)`，由业务方定时任务（如 xxl-job）调用 |
| D10 | 不引入 MQ | 同 Q9 |
| D11 | **无消息标识冗余列** | `push_message.id` 即业务消息标识 |
| D12 | **读状态由操作日志派生** | 无 read_flag/read_time 列；已读 = 存在 READ 记录 |
| D13 | **数据库层零业务约束** | 无外键/唯一键/CHECK/DEFAULT/组合主键；索引仅加速 |
| D14 | 业务实现落 **system 体系** | 契约 `system-api`、实现 `default-system-impl`、实体/Mapper `shared`，`app` 仅 HTTP 薄壳；沿用 `com.tbs.app.*` 包名 |
| D15 | **发送前拦截器链** | `IPushMessageInterceptor extends Ordered`，`support()` 命中才 `intercept()`，可脱敏/改写/富化 |

### 0.5 设计演进被否决的方案（ADR）

| 被否决方案 | 否决理由 |
|------------|----------|
| 独立"已读状态表"（稀疏 upsert） | 稀疏 upsert 依赖唯一键判定冲突，与 D13 直接冲突；并发已读会产重复行且 DB 拦不住；读状态与接收关系本是 1:1，拆表断裂读写局部性。**操作日志（append-only）达成同样的状态外置且天然幂等** |
| `message_key` 独立业务标识（含时间前缀） | 主表自增 id 已承担唯一标识；第二标识无唯一约束兜底、无跨库引用、无幂等职责，纯冗余；清理定界由 `create_time` 索引替代 |
| 复合主键 `(receiver, message_id)` | 业务逻辑不入库；代理主键 + 二级索引已覆盖查询路径 |
| 行格式极致压缩（BINARY 键/NULL 稀疏） | 目标量级（万级行/天）下物理优化收益不可测；真正决定查询速度的是访问路径（索引对齐、游标分页），这些已具备 |
| 为推送链路引入 MQ | 见 Q9 |

### 0.6 非目标

- 不做消息撤回、修改；
- 不做保留期外历史归档/聚合报表（仅物理清理）；
- 不做信令可靠投递补偿（由建连/重连后主动拉第一页兜底）；
- 不做发送幂等键（同一业务动作重复调用 = 两条消息，业务以自有业务键查重）。

### 1.3 一条消息的完整接力

```
业务方 notify  →  Service 落库(主表+fan-out+SEND日志, 一个事务)
             →  事务提交  →  逐接收人 publishSignal("tbs.push.channel.{uid}")
             →  内存源入队  →  分发器取出  →  匹配订阅该频道的在线会话
             →  编码 SIGNAL 帧下行  →  客户端收 'signal'
             →  客户端防抖 300ms  →  GET /list 拉正文  →  渲染 + 角标
阅读/点击  →  POST /read | /operate  →  写 READ/CLICK 日志  →  未读由日志派生
```

## 2. 协议层（push-api）关键约定

### 2.1 帧类型与 SIGNAL

- `FrameTypeEnum` 含 `SIGNAL("signal")`。`PushMessage.frameType` **缺省 `DATA`**（向下兼容旧 `publish` 调用方），信令场景由 `publishSignal` 显式置 `SIGNAL`。
- `JsonPushCodec.encodeMessage` 按 `frameType` 构帧；SSE 下行的**事件名取帧类型值**（`frame.getType().getValue()`），故 SIGNAL 帧在浏览器表现为 `signal` 事件、HELLO 表现为 `hello`、PONG 表现为 `pong`。
- `PushFrame(type=SIGNAL)`：`topic = 用户专属频道`、`id = 帧级 UUID`（非业务消息 id）、**`payload = null`**。消息内容绝不进信令。

### 2.2 统一连接建立流程（签票 → 建连 → 订阅）

| 时点 | 动作 | 参与 SPI |
|------|------|----------|
| ① 签票 | `POST /private/push/auth`（携带登录令牌）→ 校验身份并签发一次性 `ticket` + `sessionId` + 派生 `grantedTopics` | `IPushAuthenticator`（业务身份）、`IPushTopicGranter`（授权集） |
| ② 建连 | `GET /private/push/sse/connect?push-ticket=…`（SSE，EventSource 不能带 Header，前端用 polyfill 携带 `Authorization`）；一次性 ticket 原子消费；下发 `hello` 帧带回 `sessionId` | `IConnectionInterceptor`（`PushSessionIdentityInterceptor`：身份一致性校验 + 自动订阅本人频道） |
| ③ 订阅 | 客户端上行 `SUBSCRIBE` 帧订阅目标 topic | `ISubscriptionAuthorizer`（`GrantedTopicSubscriptionAuthorizer`：不在授权集 → 回 `1008` **拒订不断流**） |
| 上行 | `SUBSCRIBE/UNSUBSCRIBE/PING/UPLOAD` 经 `POST` 上行，帧 `type` 用**大写枚举名** | `IUploadGuard`（`PushSessionUploadGuard`：归属不符 → 回 `1009` **丢帧不断流**） |

### 2.3 授权集：三层来源 · 三个时点

授权集（会话能订阅哪些 topic）的唯一真源是 `PushCredential.grantedTopics`，在**签票时点**由三层合并派生，之后在建连、订阅两时点复用：

1. **硬编码层**：本人专属信令频道 `tbs.push.channel.{userId}`（`SignalChannelTopicGranter`）；
2. **配置层**：`tbs.push.grant-public-topics`（缺省 `[global.broadcast]`）；
3. **业务扩展层**：业务可再注册 `IPushTopicGranter` 追加（如部门公共频道）。

订阅时点 `GrantedTopicSubscriptionAuthorizer` 按"是否保留前缀 / 是否命中授权集"短路判定；`tbs.push.channel.*` 为**保留命名空间**，业务 topic 不得占用。

### 2.4 TopicMatcher

`.` 分级匹配：`*` 命中单级、`#` 命中一级或多级（仅允许作为末级）。订阅侧可写通配，发布侧写具体 topic。

### 2.5 协议错误码（ERROR 帧载荷）

| 码 | 枚举 | 语义 | 是否断流 |
|----|------|------|----------|
| 1001 | PROTOCOL_VERSION_MISMATCH | 握手版本协商失败 | 关闭 |
| 1002 | FRAME_MALFORMED | 帧无法反序列化/必填缺失 | 视场景 |
| 1003 | TOPIC_INVALID | topic 空/超长(>128)/非法字符 | 拒该操作 |
| 1004 | FRAME_TYPE_UNSUPPORTED | 不支持的帧类型（如**客户端误发 SIGNAL 上行**） | 拒该帧 |
| 1005 | SESSION_NOT_FOUND | sessionId 失效 | 拒该请求 |
| 1006 | NOT_CONNECTED | 未握手即发业务数据 | 拒该帧 |
| 1007 | INTERNAL_ERROR | 服务端内部错误 | 视场景 |
| 1008 | SUBSCRIBE_DENIED | 订阅主题不在授权集 | **拒订不断流** |
| 1009 | UPLOAD_DENIED | 上行未过归属守卫 | **丢帧不断流** |

> 错误码段预留：1xxx 协议、2xxx 传输、3xxx 会话。

## 3. 数据模型

### 3.1 建表（以实体 `@Table/@Column` 为权威来源）

三张表全部 **append-only，整个 schema 无任何 UPDATE 路径**；均为单列自增主键，**无外键、无唯一键、无组合主键**；二级索引仅为查询加速（其中日志表含一个复合索引）。

**`push_message`（主表 · 消息本体，发送后不可变）** — 实体 `PushMessageEntity`

| 列 | 约束 | 说明 |
|----|------|------|
| id | PK, IDENTITY | 即业务消息标识 |
| topic | NOT NULL, len 128 | 业务主题 |
| msg_type | NOT NULL, len 32 | 消息类型（可字典扩展） |
| title | len 255 | 标题 |
| content | — | 正文（长文本） |
| priority | NOT NULL, len 16 | 优先级（Service 缺省填充 `normal`，无 DB 默认值） |
| sender | len 64 | 发送者展示标识（审计权威见 SEND 日志） |
| url | len 512 | 点击跳转地址 |
| ext_info | — | 扩展 JSON（业务自定义，避免频繁 DDL） |
| create_time / update_time | create NOT NULL | 由审计接口自动填充 |

索引：`idx_create_time(create_time)`。

**`push_message_receiver`（接收人表 · 纯投递关系）** — 实体 `PushMessageReceiverEntity`

| 列 | 约束 | 说明 |
|----|------|------|
| id | PK, IDENTITY | 兼游标分页排序键，自增即到达序 |
| message_id | NOT NULL | `push_message.id` |
| receiver | NOT NULL | 接收用户 ID |
| create_time / update_time | create NOT NULL | 审计列 |

索引：`idx_receiver(receiver)`、`idx_create_time(create_time)`。

**`push_message_operation_log`（全链路操作日志）** — 实体 `PushMessageOperationLogEntity`

| 列 | 约束 | 说明 |
|----|------|------|
| id | PK, IDENTITY | 主键 |
| message_id | NOT NULL | 消息 ID |
| operator | 可空 | 操作人（系统/服务发起可空，身份进 ext_info） |
| op_type | NOT NULL, len 32 | SEND/READ/CLICK/… |
| op_source | len 32 | http/rpc/job/system |
| op_time | NOT NULL | 操作时间 |
| ext_info | — | 上下文扩展 JSON |
| create_time / update_time | create NOT NULL | 审计列 |

索引：`idx_operator_msg(operator, message_id)`（复合）、`idx_message(message_id)`、`idx_op_time(op_time)`。

### 3.2 建模约定

- **消息本体不随接收人复制**：主表一行、关系表每人一行；
- **读状态不落列**：`已读 ⇔ 存在 (operator=本人, message_id, op_type=READ) 记录`；
- **重复日志行无害**：同一消息多次 READ 语义不变，未读计数用 `COUNT(DISTINCT message_id)` 抵消；
- **CLICK 默认补记一条 READ**（业务规则，封装在 `recordOperation`，可调）；
- **sender 列与 SEND 日志并存**：列供列表展示，日志供行为审计（覆盖 RPC/Job 等无请求日志通道）；
- **投递关系不复制进日志**：日志记"行为事件"，关系表记"关系事实"，全链路由三源拼图。

### 3.3 数据转换规则

| 转换 | 位置 | 规则 |
|------|------|------|
| `PushNotifySendForm` → `PushMessageEntity` | Service 发送事务内 | id 由 DB 回填；校验 msgType/priority；topic 缺省 `global.broadcast`；priority 缺省 `normal`；审计接口填充时间 |
| 拦截器改写 | 校验后、落库前 | 遍历 `IPushMessageInterceptor`，`support()` 命中才 `intercept()` 返回新表单 |
| Entity + 解析结果 → `List<PushMessageReceiverEntity>` | 发送事务内 | 应用层 `LinkedHashSet` 去重（DB 无唯一约束兜底）后批量 insert |
| Entity + 发起上下文 → SEND 日志行 | 发送事务内 | operator=登录用户（无则空 + ext_info 声明）；op_source=调用通道；op_time=now |
| 三表 → `PushNotifyMessageVO` | Service 拉取 | 主表 + 接收行关联，日志表批量探查已读标注 |
| Entity → SIGNAL 帧 | `publishSignal` → `encodeMessage` | frameType=SIGNAL、topic=用户频道、id=UUID、payload=null |

### 3.4 存储访问路径

| 场景 | 索引 | 路径要点 |
|------|------|----------|
| 拉某用户消息列表 | `idx_receiver` | `receiver=? AND (cursor 为空 OR id<cursor) ORDER BY id DESC LIMIT n+1`，多取 1 判 hasMore |
| 未读列表筛选 | `idx_receiver` + `idx_operator_msg` | 边扫边过滤：取一批关联 READ 日志剔除已读，不足 limit 继续；扫描批次上限 `UNREAD_SCAN_MAX_BATCH=50` 防病态全箱扫描 |
| 未读数 | `idx_receiver` + `idx_operator_msg` | `未读 = 接收行数 − COUNT(DISTINCT message_id WHERE op_type=READ)` |
| 批量已读 | `idx_operator_msg` | 先取"属于本人的 messageIds"，剔除已有 READ 者，仅对缺失者写 READ |
| 单消息全链路 | `idx_message` | SEND 行 + receiver 行集 + READ/CLICK 行集三源拼图 |
| 物理清理 | `idx_create_time` / `idx_op_time` | 按 create_time/op_time `< deadline` 分批删，单批 `CLEANUP_BATCH=5000` |

## 4. 业务流程

### 4.1 角色与职责

| 角色 | 载体 | 职责边界 |
|------|------|----------|
| 业务方 | HTTP / `@Resource IPushNotifyService` | 决定"发什么、按什么 topic 发" |
| 拦截器链 | `IPushMessageInterceptor` | 发送前脱敏/改写/富化（可选） |
| 接收人解析器 | `INotifyReceiverResolver` | 由 topic 解析"该谁收"（业务 SPI） |
| 服务实现 | `PushNotifyServiceImpl` | 事务编排、落库、派生、发布信令 |
| 门面 | `IPushEndpoint` | 把信令交给协议层 |
| 分发器 | `AbstractPushDispatcher` | 匹配在线订阅会话、下行、留痕 |
| 客户端 | 前端/SDK | 收信令→拉取→渲染→回传处理 |

### 4.2 发送（`PushNotifyServiceImpl.send`）七步

```
① validateSendForm         契约校验（AssertUtil 链式断言 + i18n）
② 拦截器链                  for(ObjectProvider<IPushMessageInterceptor>) support()?intercept()
③ resolveReceivers          遍历 List<INotifyReceiverResolver>，supports 命中者累加，LinkedHashSet 去重
④ buildMessageEntity        表单 → 主表实体（缺省填充 topic/priority/source）
⑤ TransactionUtil.executeTransaction(doSend)   ——编程式事务（避免自调用注解失效）——
     ├─ insert push_message（回填 id）
     ├─ batch insert push_message_receiver（fan-out）
     └─ insert push_message_operation_log(SEND)
⑥ publishSignals(receivers)  事务提交后；pushEndpointProvider.getIfAvailable() 取门面（未启用则跳过）；
                            逐接收人 publishSignal("tbs.push.channel.{uid}", null)，单条 try-catch
⑦ 返回 PushSendResultVO      {messageId, topic, msgType, receiverCount, signalCount}
```

- **入库即成功**：步骤⑤事务提交即视为发送成功；步骤⑥信令失败或推送未启用**不回滚、不改成功语义**，仅记日志。
- `signalCount` = 实际成功发布的信令数（推送未启用或全部失败时为 0），与 `receiverCount`（落库关系行数）分开，供调用方区分"落库规模"与"即时触达尝试"。
- **接收人为空是合法状态**（仅落库、无信令，`receiverCount=0`）。

### 4.3 topic 前缀解析规则（默认解析器 `TopicPrefixNotifyReceiverResolver`）

| topic 形态 | 解析动作 | 数据源 |
|------------|----------|--------|
| 空 / `global.broadcast` | 全体激活用户 | `ISystemUserService.queryAllActiveUserIds()` |
| `user.name.{userName}` | 按用户名精确匹配 | `queryUserIdsByUserName` |
| `user.search.{keyword}` | 按用户名前缀搜索 | `queryUserIdsByUserNamePrefix` |
| `tbs.push.channel.*` | **拒绝解析**（`supports=false`），防业务消息伪装信令 | — |
| 其他未知 topic | 返回空集（仅落库审计语义） | — |

> 业务方注册自定义 `INotifyReceiverResolver` Bean 即覆盖本默认实现（`@ConditionalOnMissingBean`）；亦可并存多个，Service 侧对全部命中结果累加去重。

### 4.4 接收 → 拉取 → 处理

- **触发拉取的两条路径**：① 收到 `signal` 事件；② 建连/重连 `hello` 成功后主动拉第一页（兜底离线期间与丢失的信令）。前端对 signal 做 **300ms 防抖**再拉取。
- **拉取**：`GET /list?cursor=&limit=20&readFlag=all|unread`，到达序倒序、含已读；按消息 id 合并去重后渲染。
- **处理回传**：阅读走 `POST /read`（批量、幂等）；点击等扩展操作走 `POST /operate`（CLICK 默认补记 READ）。

### 4.5 读状态与未读的派生

```
已读(用户u, 消息m)  ⇔  ∃ 日志(op_type=READ, operator=u, message_id=m)
未读数(u)          =  COUNT(receiver 行 WHERE receiver=u)
                     − COUNT(DISTINCT message_id WHERE operator=u AND op_type=READ)
```

`markRead(ids)`：取"属于 u 的 ids"∩"尚无 READ 的 ids"，仅对差集写 READ 日志，返回实际写入数（幂等，重复调用第二次为 0）。

### 4.6 清理（`cleanupBefore(Date deadline)`）

契约方法与 `send` 同属 `IPushNotifyService`，**不内置调度**；按 `create_time`/`op_time < deadline` 对三表分批物理删除（单批 5000），返回清理总行数。由业务方定时任务（如 xxl-job）按需调用。未落库依赖唯一键，故删除顺序不受外键约束（本无外键）。

### 4.7 与旧 DATA 链路对比

| 维度 | 旧 DATA（`/private/push/send` 已移除） | 新 SIGNAL + 拉取 |
|------|----------------------------------------|------------------|
| 载荷 | DATA 帧携带全量内容 | 信令空载荷，正文走拉取 |
| 持久化 | 内存源，重启即清 | DB 三表 append-only |
| 接收人 | topic 广播，无模型 | fan-out 到 receiver 表 |
| 历史/未读/翻页 | 无 | 分页接口 + 日志派生 |
| 编程能力 | `IPushEndpoint.publish` | 并存：`publish`(DATA) + `publishSignal`(SIGNAL) |

> 当前前端仅监听 `hello/signal/pong/error`，**不再订阅 DATA**；DATA 仅作为 `publish` 编程能力保留。

## 5. 接口与扩展契约

### 5.1 HTTP 端点（`PrivatePushMessageController`，基路径 `/private/push/message`）

> 均在 `/private/**`，须携带有效登录令牌，由项目认证体系统一鉴权；响应用 `AjaxResult` 统一包装，下文示例仅示 `data` 部分。

| 方法 | 路径 | 入参形态 | data 返回 |
|------|------|----------|-----------|
| POST | `/notify` | `@RequestBody PushNotifySendForm` | `PushSendResultVO` |
| GET | `/list` | **query 绑定** `PushMessageQueryForm`（cursor/limit/readFlag） | `PushMessagePageVO` |
| GET | `/unread-count` | 无 | `long` |
| POST | `/read` | `@RequestBody List<Long>`（**裸数组**，≤100） | `int` |
| POST | `/operate` | `@RequestBody PushMessageOperateForm`（messageId/opType/extInfo） | `int` |
| GET | `/chain` | **query 参数** `?messageId=` | `PushMessageChainVO` |

入参形态三处易错点：`/list` 用 GET 查询串绑定对象（非 JSON body）；`/read` 直接以 `[1001,1002]` 裸数组为体（非 `{messageIds:[...]}`）；`/chain` 用查询参数而非路径变量。

### 5.2 契约与示例

**发送** `POST /notify`，请求体 `PushNotifySendForm`（仅 `msgType` 必填，其余可选）：

```json
{ "msgType": "notify", "title": "工单已分派", "content": "#2048 已分派给您",
  "priority": "high", "topic": "user.name.zhangsan", "sender": "系统",
  "url": "/ticket/2048", "extInfo": { "ticketId": 2048 }, "source": "http" }
```

响应 `data`（`PushSendResultVO`）——**送达规模以 `receiverCount` 为准**：

```json
{ "messageId": 10086, "topic": "user.name.zhangsan", "msgType": "notify",
  "receiverCount": 1, "signalCount": 1 }
```

**拉取** `GET /list?limit=20&readFlag=unread`，响应 `data`（`PushMessagePageVO`）：

```json
{ "list": [ { "messageId": 10086, "topic": "user.name.zhangsan", "msgType": "notify",
      "title": "工单已分派", "content": "#2048 已分派给您", "priority": "high",
      "sender": "系统", "url": "/ticket/2048", "createTime": "2026-10-08 10:00:00",
      "readFlag": false, "readTime": null } ],
  "cursor": 30021, "hasMore": true }
```

下一页传 `&cursor=30021`。

**已读** `POST /read` 体 `[10086, 10087]` → `data: 2`（重复调用返回 0，幂等）。
**操作** `POST /operate` 体 `{ "messageId": 10086, "opType": "CLICK", "extInfo": "message-center" }` → `data: 2`（CLICK 补记一条 READ）。
**全链路** `GET /chain?messageId=10086` → `data`（`PushMessageChainVO`）：

```json
{ "message": { "messageId": 10086, "title": "工单已分派", "readFlag": true, "readTime": "..." },
  "sendEvent": { "operator": 9527, "opType": "SEND", "opSource": "http", "opTime": "...", "extInfo": null },
  "receivers": [ 1001, 1002, 1003 ],
  "operations": [ { "operator": 1001, "opType": "READ", "opSource": "http", "opTime": "..." } ] }
```

### 5.3 SPI 扩展点总表

| 扩展点（契约类 · 包） | 时机 | 默认实现 | 覆盖方式 |
|------------------------|------|----------|----------|
| `INotifyReceiverResolver`（system-api `com.tbs.app.service.push`） | 发送·解析接收人 | `TopicPrefixNotifyReceiverResolver` | `@ConditionalOnMissingBean`，业务注册即替换；可多 Bean 并存，Service 累加去重 |
| `IPushMessageInterceptor` | 发送·落库前 | 无 | 注册多个，`Ordered` 排序，`support()` 命中才 `intercept()` |
| `IPushAuthenticator` | 签票·身份 | `PushUserAuthenticator` | `@Primary`（协议层有 Noop 兜底，按类型注入恒选业务实现） |
| `IPushTopicGranter` | 签票·授权集 | `SignalChannelTopicGranter` | 可追加多 Bean 合并授权集 |
| `ISubscriptionAuthorizer` | 订阅·鉴权 | `GrantedTopicSubscriptionAuthorizer` | 注册即覆盖 |
| `IConnectionInterceptor` | 建连·一致性 | `PushSessionIdentityInterceptor` | 可多 Bean，协议层按需收集 |
| `IUploadGuard` | 上行·认人 | `PushSessionUploadGuard` | 注册即覆盖 |
| `IPushMessageStore` | 信令暂存 | 内存源 | 容量满淘汰最早；可换分布式实现（本期不需要） |
| `IPushEndpoint` | 程序化下发 | `DefaultPushEndpoint` | 业务 `@Autowired` 即用 `publish`/`publishSignal` |

### 5.4 协议层编程 API

```java
// 全量 DATA（旧能力，仍保留）
String publish(String topic, String payload);
// 空载荷信令（新链路发送侧唯一出口）；消息中心按 "tbs.push.channel.{receiver}" 逐人发布
String publishSignal(String topic, String payload);
```

`publishSignal` 产出的帧：`frameType=SIGNAL`、`id=` 帧级 UUID、`payload` 原样（消息中心传 `null`）。SSE 下行事件名即 `signal`。

### 5.5 调用约束

1. `msgType` 必填；`priority ∈ {low,normal,high,urgent}`（缺省 normal）；`topic` ≤128 字符（缺省 `global.broadcast`）；`title` ≤255、`url` ≤512。
2. `tbs.push.channel.*` 为保留命名空间，业务发送 topic 不得占用（默认解析器直接拒解析）。
3. `/read` 单次 ≤100（`MAX_READ_BATCH`）；`/list` `limit` 缺省 20、上限 100（`MAX_PAGE_LIMIT`）。
4. HTTP 成功 ≠ 送达：以 `receiverCount` 判定实际接收人规模，`receiverCount=0` 表示未解析到接收人（如用户名不存在）。
5. 非本人接收关系的消息，`/read`、`/operate` 静默跳过（不计入返回数）。
6. 重复 READ/重复发送均无害（append-only，无幂等键）。
7. 未读筛选页内条数可能少于 `limit`（边扫边过滤），翻页以 `cursor` 为准、`hasMore` 判断续拉。

## 6. 客户端接入概览

> 端到端可运行案例（curl / Vue / Java SDK / C# SDK / Python / Go）见同目录 `push-usage-guide.md`，此处仅概览职责矩阵。

| 客户端 | 传输 | 建连方式 | 信令处理 |
|--------|------|----------|----------|
| 浏览器（`app-ui-vue/src/push`） | SSE | `EventSourcePolyfill` 携带 Authorization 头 + `?push-ticket=` | `signal` 事件→防抖拉取 |
| Java SDK（`sdk`） | SSE | `TbsClient.sse()`（OkHttp EventSource） | `SseFrameListener.onFrame`(SIGNAL) |
| C# SDK（`sdk-csharp`） | SSE | `SsePushClient.Connect()` | `SignalReceived` 事件 |
| 自研（curl/Python/Go） | SSE | HTTP 流式读 `event:signal` | 解析后调 `/list` |

前端关键约定（`src/push`）：

1. `sse-client.js` 仅监听 `hello/signal/pong/error`，**不监听 DATA**；`hello` 成功后主动拉第一页兜底；
2. 每次建连实时取 `getToken()`，不依赖 connect 快照（兼容令牌无感刷新）；换票重连，不用 EventSource 原生自动重连（ticket 已消费）；
3. `store/modules/push.js`：signal **300ms 防抖**再拉取、`MAX_MESSAGES=200` 内存上限、`firstPullDone` 首拉不弹通知、`persistRead` 为本地扩展点（当前空实现）；
4. 未读角标以服务端 `/unread-count` 为准（内存计数仅作展示近似）；
5. 管理端发布 `admin.js.publishNotify`：`scope=all` 走单次 `global.broadcast`，`scope=users` 逐人 `user.name.{username}`，`receiverCount>0` 才算成功；
6. 点击通知中心条目走 `POST /operate`（`opType=CLICK`，`extInfo='message-center'`），服务端补记 READ。

服务端不硬编码用户可读文案，统一走消息源：

| 范围 | 资源 | 常量类 |
|------|------|--------|

## 8. 配置与装配

### 8.1 本项目实际配置（`app/src/main/resources/application-tbs.yml`）

```yaml
tbs:
  system:
    enable: true      # 业务 Bean（Service/Resolver）开关
  push:
    enable: true      # 协议层 + 安全 SPI 开关
    transport: sse    # sse | websocket（仅 WebSocket 侧条件读取，见 8.2）
    heartbeat-timeout-millis: 600000
    dispatch:
      scheduler: job  # 分发调度方式（走 PushDispatchJob）
```

启动类 `AppApplication` 标注 `@EnableTbsPush @EnableTbsPushSse`，`app/pom.xml` 依赖 `push-sse-impl`。

### 8.2 装配语义（`BuisnessBeanConfig`）

| Bean | 条件 |
|------|------|
| `IPushNotifyService`→`PushNotifyServiceImpl` | `tbs.system.enable=true` + `@ConditionalOnMissingBean` |
| `INotifyReceiverResolver`→`TopicPrefixNotifyReceiverResolver` | `tbs.system.enable=true` + `@ConditionalOnMissingBean` |
| `IPushAuthenticator`→`PushUserAuthenticator` | `tbs.push.enable=true` + `@Primary` |
| `IPushTopicGranter`→`SignalChannelTopicGranter` | `tbs.push.enable=true` |
| `ISubscriptionAuthorizer`→`GrantedTopicSubscriptionAuthorizer` | `tbs.push.enable=true` |
| `IConnectionInterceptor`→`PushSessionIdentityInterceptor` | `tbs.push.enable=true` |
| `IUploadGuard`→`PushSessionUploadGuard` | `tbs.push.enable=true` |

**两个独立开关**：业务消息中心能力取决于 `tbs.system.enable`；协议层与安全 SPI 取决于 `tbs.push.enable`。信令发布对 `IPushEndpoint` 用 `ObjectProvider.getIfAvailable()` 延迟获取——**推送未启用时发送降级为"仅落库、不发信令"，不报错**。

> `PushProperty.enable` 字段 Java 缺省为 `true`，但 `@ConditionalOnProperty(havingValue="true")` 无 `matchIfMissing`，故**必须显式配 `tbs.push.enable=true`** 上述 SPI Bean 才装配。`transport` 不是 `PushProperty` 字段，仅 WebSocket 侧 `@ConditionalOnProperty(name="transport", havingValue="websocket", matchIfMissing=true)` 读取；SSE 侧装配不依赖它。

### 8.3 从 0 到 1 最小装配

1. **依赖**：应用模块引入 `push-sse-impl`（或 `push-websocket-impl`）与 `default-system-impl`；
2. **开关**：`tbs.system.enable=true`、`tbs.push.enable=true`；
3. **启用注解**：启动类加 `@EnableTbsPush` + `@EnableTbsPushSse`（或对应传输）；
4. **建表**：三表（`push_message`/`push_message_receiver`/`push_message_operation_log`），可 JPA 自动建或执行 DDL；
5. **扫描**：确认 `PushMessageScanConfig` 的 `@MapperScan("com.tbs.shared.mapper.push")` / `@EntityScan("com.tbs.shared.pojo.entity.push")` 生效；
6. **接收人**：默认按 topic 前缀查用户表；特殊规则注册自定义 `INotifyReceiverResolver`；
7. **客户端**：签票→建连→订阅 `tbs.push.channel.{userId}`；
8. **验证判据**：`POST /notify` 返回 `receiverCount>0`；在线客户端收到 `signal`；`GET /list` 能拉到该消息；`GET /unread-count` 计入；`POST /read` 后未读减、`readFlag=true`。

## 9. 与旧稿的差异及演进

### 9.1 本次复核对旧「设计定稿」的订正（以代码为准）

| # | 旧稿表述 | 代码实况 |
|---|----------|----------|
| 1 | 业务主体在 `app` 模块 | 契约在 `system-api`、实现在 `default-system-impl`、实体/映射在 `shared`，`app` 仅 HTTP 薄壳；但**沿用 `com.tbs.app.*` 包名** |
| 2 | 发送 `/private/push/notify`、拉取 `/private/push/messages` | 基路径统一 `/private/push/message`：`/notify`、`/list`、`/unread-count`、`/read`、`/operate`、`/chain` |
| 3 | D2 旧 `/private/push/send` "完整保留" | 当前**无任何控制器暴露 `/private/push/send`**；DATA 仅保留为 `IPushEndpoint.publish` 编程能力；`app/form/PushNotifyMessage` 为无引用遗留类，`PrivatePushMessageController` 注释"保持不变"已过期 |
| 4 | 未提拦截器扩展点 | 新增 `IPushMessageInterceptor`（D15），发送前可改写表单 |
| 5 | 未细化默认接收人解析 | 补 `TopicPrefixNotifyReceiverResolver` 前缀规则（§4.3） |
| 6 | 未展开授权集/身份落地类 | 补三层三时点与 5 个业务 SPI 实现类（§2.3、§5.3） |
| 7 | 未读数/清理算法缺失 | 补派生公式与 `cleanupBefore` 分批（§4.5、§4.6） |
| 8 | "零组合索引" | 日志表实为**复合索引** `idx_operator_msg(operator,message_id)` |
| 9 | 建表 SQL（`DATETIME`） | 以实体 `@Column` 为权威；时间列精度/字符集以实际 DDL 为准 |
| 10 | `enable` 默认 false | `PushProperty.enable` 字段缺省 true，但条件装配需显式配 true |

### 9.2 其余实现期事实

- SSE 端点薄壳（`SsePushAuthController`/`SsePushController` + `SseUploadForm`）在 **`app` 模块**，不在 `sse-impl`；
- `PushFrameConstants.SSE_EVENT_PREFIX`（`"push-"`）当前未被使用；
- 协议层 `ConnectionInterceptorChain` 已移除，改由 `ObjectProvider<IConnectionInterceptor>` 按需收集。

### 9.3 增长与演进路径（触发条件）

| 压力信号 | 演进手段 |
|----------|----------|
| 接收人表规模增大、翻页变慢 | 按 `receiver` 水平分片 / 按 `create_time` 分区 |
| 未读计数成为热点 | 物化计数（缓存 + 日志增量校正），仍不回退到状态列 |
| 保留期数据膨胀 | 业务定时任务调 `cleanupBefore`；冷数据归档表 |
| 广播消息 fan-out 行暴增 | 大 topic 走"共享收件箱"特殊解析器（不 fan-out，读时按订阅判定）——需业务 SPI 定制 |
