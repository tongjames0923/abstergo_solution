# 版本管理相关模块现状梳理

> **梳理日期**：2026-11-27  
> **梳理范围**：`abstergo_solution` 仓库内全部源码、POM、配置、规范文档，以及 Git 仓库实际分支/标签状态  
> **说明**：文中「未发现」指在当前仓库范围内未找到对应实现或约定，不代表外部 CI 平台/运维系统中不存在。

## 0. 现状总览

项目并不存在单一统一的“版本管理系统”，而是由**四套相互独立但彼此关联的版本体系**构成：

| 体系 | 版本标识 | 管理对象 | 主要载体 |
|---|---|---|---|
| 业务应用版本 | `versionCode`（整数）+ `versionName`（自由字符串）+ `versionType`（阶段） | 客户端应用发布包 | `shared-pojo` / `system-api` / `default-system-impl` / `app` / Vue 管理端 |
| 网关构建版本与视图版本 | `app.gateway.version`（如 `1.6`）、`viewVersion`（`MAX(id)`） | 后端运行实例、动态路由配置 | `app/pom.xml`、`application.yml`、`PublicGatewayVersionController`、`dynamic-view-route` |
| 客户端更新链路 | `.installed-version` 中的整数 `versionCode` | 本地已安装版本 | `sdk`、`updater`、`updater-gui`、`sdk-csharp` |
| 工程依赖版本治理 | `1.0-SNAPSHOT`、`tbs.version`、各三方库版本属性 | Maven 模块与三方依赖 | 根 `pom.xml`、`package.json`、Go module |

其中，**业务应用版本**是唯一具备完整状态机和生命周期管理的一套；其余三套分别服务于部署验证、客户端升级和构建依赖收敛。

## 1. 版本号命名与递增规则

### 1.1 业务应用版本字段

核心定义位于 `shared/shared-pojo/src/main/java/com/tbs/shared/pojo/entity/version/AppVersionEntity.java`，表结构见 `etc/sql_file/app_system_struct.sql:67-88`。

| 字段 | 类型 | 含义 | 约束现状 |
|---|---|---|---|
| `appKey` | `varchar(64)` | 应用标识，如 `backend-service` | 必填，按 `appKey + platform` 区分版本序列 |
| `versionCode` | `bigint`（Java `Long`） | 内部版本号，注释为“递增整数，用于版本比较” | **仅做唯一性校验，无递增校验**；前端输入 `:min="1"` |
| `versionName` | `varchar(64)` | 外部展示版本名，如 `1.2.0` | 必填，但**无格式校验**，按普通字符串存储 |
| `versionType` | `int` | 阶段类型：`1=release, 2=beta, 3=alpha, 4=rc` | 后端按 `AppVersionTypeEnum` 校验合法性 |
| `platform` | `varchar(32)` | 目标平台（`android/ios/windows/macos/linux`） | 必填；前端下拉固定 5 个选项 |
| `flag` | `int` | 生命周期状态，见 1.2 | 新建强制置为 `DRAFT(0)` |
| `buildInfo` / `releaseNote` | `text` | 构建元数据 / 更新日志 | 可选，随版本下发 |
| `releaseTime` / `offlineTime` | `datetime(6)` | 发布 / 下线时间 | 分别在 `release` / `offline` 时写入 |

### 1.2 实际递增与命名规则

1. **没有 SemVer 解析/比较逻辑**。仓库中未发现 semver 依赖、`x.y.z` 解析函数、`increment`/`bump` 实现，`versionName` 仅作为展示字符串。
2. **唯一性校验代替递增校验**：`AppVersionServiceImpl.validateDuplicateVersionCode()`（`system/default-system-impl/.../AppVersionServiceImpl.java:233-241`）只校验同一 `appKey + versionCode + platform` 且非归档版本不能重复；**没有“新版本必须大于历史最大版本”的约束**。
3. **“最新版本”由比较得出**：`queryLatestReleased()` 取 `flag=RELEASE` 且 `versionType=RELEASE(1) 或 NULL（历史数据兜底）` 后按 `versionCode` 倒序第一条（同文件 `208-215`）；升级判断也是 `currentVersionCode < latest.versionCode`。因此若人为填写较小的 `versionCode`，会影响升级判定。非正式版仅指 `versionType in (2,3,4)`，由 `prereleaseUpdate` 分支返回，不参与主数据。
4. **编辑受限、克隆需手工填号**：前端 `VersionList.vue:80-82` 中 `versionCode` 编辑时禁用；`handleClone()`（同文件 `218-229`）复制版本时清空 `versionCode`/`versionName`，由维护人员手工填写。后端 `compareAndUpdateValue()` 允许草稿状态修改 `versionCode` 并重新校验重复。
5. **命名口径不统一**：Git 标签用 `v1.4`/`v1.5`/`v1.6`（带 `v` 前缀），网关构建版本是 `1.6`（无前缀），Maven 工程版本是 `1.0-SNAPSHOT`，前端包版本是模板遗留的 `4.4.0`。

### 1.3 阶段类型、生命周期状态与兼容动作编码

| 枚举 | 编码 | 说明 | 位置 |
|---|---|---|---|
| `AppVersionTypeEnum` | `1=release, 2=beta, 3=alpha, 4=rc` | 沿用前端历史约定，与成熟度无关 | `shared/shared-pojo/.../enums/AppVersionTypeEnum.java:19` |
| `AppVersionFlagEnum` | `DRAFT=0, PENDING=2, RELEASE=1, OFFLINE=-1, ROLLED_BACK=-2, ARCHIVED=-3` | 正数=活跃态，负数=终止态；`ARCHIVED` 兼作逻辑删除终态 | `shared/shared-pojo/.../enums/AppVersionFlagEnum.java:24-25` |
| `AppVersionCompatibilityActionEnum` | `FORCE=1, RECOMMEND=2, NOTIFY=3` | 实际是**值越小强制程度越高**（与枚举注释相反） | `shared/shared-pojo/.../enums/AppVersionCompatibilityActionEnum.java:17-25` |

### 1.4 网关构建版本与视图路由版本

- **构建版本**：`app/pom.xml:24` 定义 `project.app.version=1.6`；`app/src/main/resources/application.yml:53-58` 通过资源过滤注入 `app.gateway.version: ${APP_GATEWAY_VERSION:@project.app.version@}`；`spring-boot-maven-plugin` 的 `build-info` goal 生成 `META-INF/build-info.properties`（`app/pom.xml:122-133`）。
- **解析优先级**（`PublicGatewayVersionController.java:29-35, 108-119`）：`APP_GATEWAY_VERSION` 启动参数/环境变量 → `build-info.properties` → 资源过滤注入值（含 `@` 视为无效）→ `unknown`。
- **视图版本**：`viewVersion` 由 `IViewRouteService.getViewVersion()` 返回，语义是版本表 `MAX(id)`，无记录返回 `0`（`dynamic-view-route/README.md:134`）。前端 `app-ui-vue/src/router/index.js:151-155, 207-209` 将其写入本地缓存用于菜单更新比对。视图路由自身还有组内序号 `versionNo`（`v1`、`v2`…）与全局版本 ID，见 `ViewRouteVersionModel.java`。

### 1.5 客户端本地版本

`updater` 将最新 `versionCode` 写入 `.installed-version` 文件作为下次启动的 `currentVersionCode`（`updater/.../config/UpdaterConfig.java:88-95`）；无记录或文件损坏时 `readLocalVersion()` 返回 `-1`（同文件 `292-313`）。配置模板 `updater.properties.template:27-28` 默认 `app.currentVersionCode=0`。

### 2.2 文档约定的分支策略

来源：`docs/guideline/06-部署与运维规范.md:38-52, 133-152`。

- Jenkins 流水线从 Gitee 拉取源码，`BRANCH_NAME` 参数化，构建时指定分支。
- `main` 为可发布分支；功能分支经合并请求、Code Review 通过后进入 `main`；禁止直接向 `main` push 未评审代码。
- 紧急 hotfix 允许先处理后补流程。
- 发布检查单包含：代码已合入 `main`、SQL 脚本提交、Nacos 配置对比确认、构建产物版本号正确、备份上一版本产物、发布后冒烟与日志巡检。

### 2.3 缺失项

- 仓库内**未发现**实际 CI/CD 定义文件（无 `Jenkinsfile*`、`.gitlab-ci.yml`、`.github/` 工作流），流水线仅以文档形式描述。
- **未发现**成文的标签命名规范、`release/*` 分支约定、自动打标签脚本或 Git hook。
- `app-ui-vue/.travis.yml` 是遗留配置（`node_js: 10`，`script: npm run test`），与 06 分册规定的前端 Node 16 环境不一致，且当前 scripts 中并无 `test` 脚本（只有 `test:unit`/`test:ci`）。
- 除 Gitee Issue 模板（`.gitee/ISSUE_TEMPLATE/`）与 `.gitignore` 外，未发现其他版本管理相关仓库配置。

## 3. 依赖版本的控制策略

### 3.1 Maven：根 POM 作为唯一版本源

`pom.xml` 定位为“统一版本管理、全局依赖、插件配置”（`pom.xml:43-46`）：

- 继承 `spring-boot-starter-parent:3.3.5`；工程坐标 `com.tbs:solution:1.0-SNAPSHOT`；编译级别 JDK 21。
- 版本属性集中在 `pom.xml:49-102`：框架（`spring.boot.version=3.3.5`、`spring.cloud.version=2023.0.3`、`spring.cloud.alibaba.version=2023.0.1.2`、`dubbo.version=3.3.4`）、数据库/ORM（`mysql.version=9.7.0`、`jkit.version=2.0.4`）、中间件（`redisson.version=3.52.0`、`minio.version=8.5.7`、`okhttp3.version=4.12.0`）等。
- `tbs.version=1.0-SNAPSHOT`（`pom.xml:99-101`）与 `project.version` 解耦，注释明确“避免个别模块单独改发布版本时污染依赖管理”；根 POM 中共有 43 处 `${tbs.version}` 引用，用于统一声明内部模块版本。
- `dependencyManagement` 中 BOM 导入顺序有强制约定：`spring-boot-dependencies` 必须最先，以防 `dubbo-bom` 将 Spring 降级到 `javax`（`pom.xml:143-175`）。
- `pluginManagement` 统一管理 `maven-javadoc-plugin:3.3.0`、`maven-source-plugin:3.2.0`、`maven-compiler-plugin:3.13.0`（`pom.xml:511-555`）。
- **未发现** `maven-release-plugin`、`versions-maven-plugin`、`flatten-maven-plugin`、`maven-deploy-plugin`。

### 3.2 模块声明惯例

- 子模块继承根 POM（如 `app/pom.xml:5-12`），内部依赖普遍**不写 `<version>`**，由根 `dependencyManagement` 管控。
- `app` 自身保留 `1.0-SNAPSHOT`，并单独定义业务相关的 `project.app.version=1.6`。
- `updater/pom.xml` 仅声明 Jackson 一个传递依赖；`sdk/pom.xml` 仅声明 OkHttp/Jackson/SLF4J；版本均由父 POM 管控，不自行指定。
- 需注意：根 POM 仍保留全局 `<dependencies>`（`pom.xml:104-136`），所有子模块被动继承 `spring-dotenv`、Dubbo starter、Lombok 等，存在“全局依赖扩大依赖面”的治理空间。

### 3.3 前端依赖

`app-ui-vue/package.json`：

- 包名仍为模板名 `vue-admin-template`，`version: 4.4.0`，**不是业务发布版本**。
- 生产依赖混用精确版本与 `^` 范围（如 `axios: 0.18.1`、`element-ui: 2.15.14`、`vue: 2.6.10`，而 `@fortawesome/fontawesome-free: ^7.0.0`、`echarts: ^6.0.0`）；devDependencies 多为精确版本（`@vue/cli-*: 4.4.4`）。
- `engines.node >=8.9` 与部署规范中的 Node 16 不一致。
- **未发现** `package-lock.json` / `yarn.lock` / `pnpm-lock.yaml`，无法锁定传递依赖。

### 3.4 其他语言

- Go：`dubbo-go-starter/go.mod`、`dubbo-db-demo/go.mod` 及对应 `go.sum` 独立管理，按 06 分册不纳入 Maven/Jenkins fat jar 链路。
- C#：`sdk-csharp` 为独立 solution/csproj，非 Maven 模块。

## 4. 版本发布流程与各环节状态

### 4.1 业务版本生命周期状态机

接口契约：`system/system-api/.../service/version/IAppVersionService.java:11-14, 28-68`；实现：`system/default-system-impl/.../impl/version/AppVersionServiceImpl.java:136-206`。所有流转方法均标注 `@Transactional(rollbackFor = Exception.class)`。

| 操作 | 前置状态 | 后置状态 | 副作用 / 校验 |
|---|---|---|---|
| 新建（`insertNew`） | — | `DRAFT(0)` | 必填项、类型合法性、版本号唯一性校验 |
| `submit` | `DRAFT(0)` | `PENDING(2)` | 非草稿拒绝 |
| `release` | `PENDING(2)` | `RELEASE(1)` | 写入 `releaseTime` |
| `offline` | `RELEASE(1)` | `OFFLINE(-1)` | 写入 `offlineTime` |
| `rollback` / `rollbackAndRestore` | `RELEASE(1)` | `ROLLED_BACK(-2)` | 旧 `rollback` 仅标记（已废弃）；`rollbackAndRestore` 会把最近一个旧版本恢复为 `RELEASE(1)` |
| `archive` | `OFFLINE(-1)` | `ARCHIVED(-3)` | `ARCHIVED` 同时是逻辑删除终态，查询默认排除 |

编辑与删除仅允许草稿态；`ARCHIVED` 版本不参与重复校验，也不参与最新发布版本查询。

### 4.2 管理端接口与页面

| 环节 | 实现 | 说明 |
|---|---|---|
| 版本 CRUD / 生命周期 | `app/.../privates/version/AppVersionController.java`，前缀 `/private/admin/app-version` | `submit/release/offline/rollback/archive/{id}` 等；权限点 `API.DEV.VERSION.QUERY/SAVE/DELETE` |
| 安装包 | `app/.../privates/version/AppPackageController.java`，前缀 `/private/admin/app-package` | 文件上传/下载走统一 OSS 接口，按 `versionId` 关联 |
| 兼容策略 | `app/.../privates/version/AppVersionCompatibilityPolicyController.java`，前缀 `/private/admin/app-version-policy` | 策略 CRUD、启用/禁用、管理端升级检查 |
| 前端页面 | `app-ui-vue/src/views/admin/version/index.vue`（容器）、`VersionList.vue`（列表/表单/生命周期按钮）、`PolicyList.vue`（策略） | API 封装统一在 `src/api/app-version.js` |
| Bean 装配 | `BuisnessBeanConfig.java:199-218` | 三个版本服务受 `tbs.system.enable=true` 控制，且带 `@ConditionalOnMissingBean` 兜底 |

### 4.3 兼容策略与升级检查

`AppVersionCompatibilityPolicyServiceImpl.evaluateCompatibility()`（`system/default-system-impl/.../AppVersionCompatibilityPolicyServiceImpl.java:152-197`）：

1. 查询最新已发布版本，`needUpdate = currentVersionCode < latest.versionCode`。
2. 命中启用策略时按目标应用/平台、源应用最新版本、目标最低兼容版本筛选；`currentVersionCode < minCompatVersion` 时取 `action` **最小值**作为最强动作（同文件 `180`）。
3. 下载地址优先外部直链，否则生成 OSS 预签名 URL，有效期 86400 秒（24 小时）（同文件 `207-225`）。
4. 策略只能作用于已登记版本的应用，通过 `listAppKeys()` 校验（同文件 `236-240`）。
5. 公开接口 `POST /public/app-update/check` 无需认证（`PublicAppVersionUpdateController.java:31-56`）；返回 `needUpdate`、`action`、最新版本信息与下载地址（`AppVersionUpdateCheckVO.java`）。若客户端上报的 `currentVersionCode` 对应已下线/已回滚版本，另返回 `currentVersionDeprecated=true`、`currentVersionFlag` 与 `currentVersionName` 用于提示，不改变 `needUpdate` 语义。

### 4.4 构建、部署与验证

- **后端**（文档描述的 Jenkins 流水线）：Gitee 拉源码（`BRANCH_NAME` 参数化）→ `mvn clean package -DskipTests` → 归档 `app/target/*.jar` → 传输至 `DEPLOY_DIR` 并重启。
- **前端**：Node 16 执行 `npm install && npm run build:prod`，产物 `dist/` 部署 Nginx；构建前要求 `npm run lint` 通过。
- **Go 提供者**：独立编译二进制 + `service.json`，不纳入 fat jar 链路。
- **发布后验证**：`/public/gateway/version` 返回预期版本；Dubbo Admin 可见服务；健康检查与冒烟；日志巡检 10 分钟。
- **回滚**：换回上一版本 jar/dist + Nacos 配置回退；发布检查单要求提前备份。
- **现状**：仓库内无流水线脚本，上述流程为规范文档描述；未发现 `CHANGELOG.md` 或自动化变更记录，更新日志由版本实体的 `releaseNote` 承载。

### 4.5 客户端更新链路

| 组件 | 职责 | 关键状态/说明 |
|---|---|---|
| `sdk` | 升级检查 + 下载（多镜像容灾） | `IUpdateApi.checkUpgrade/downloadAll`；**不含部署与版本持久化**（`IUpdateApi.java:8-14`） |
| `updater` | 检查 → 下载 → 部署脚本 → 版本回写 | `autoUpdate()` 一键链路；支持 `checkForUpdate()` + `installUpdate()` 两段式；`downloadUpdate(UpdateInfo)` 与 `executeDeployScript(File)` 已 `@Deprecated`（`AutoUpdater.java:253-257, 313-320`） |
| 部署脚本 | `deploy.sh`（`lsof` 停旧进程 + `nohup java -jar`）、`deploy.bat`（`netstat` + `taskkill` + `start`） | 脚本**后台启动、不等待结束**，部署结果由调用方确认（`AutoUpdater.java:259-304`） |
| `updater-gui` | Swing 演示程序 | 依赖 `updater`，`maven-assembly-plugin:3.6.0` 打 fat JAR |
| `sdk-csharp` | C# 侧更新客户端模型 | 非 Maven 模块 |

### 4.6 各环节状态一览

| 环节 | 自动化程度 | 当前状态 |
|---|---|---|
| 版本录入 | 手工 | 前端填写，克隆需手工填新版本号 |
| 状态流转 | 半自动 | 五个操作均可点击触发，服务端强校验前置状态 |

| 变更记录 | 手工 | 无 CHANGELOG，依赖 `releaseNote` 与 guideline 文档末尾记录 |

| 已解决 | **版本类型编码前后端不一致** | 后端枚举与 SQL 注释已调整为 `1=release,2=beta,3=alpha,4=rc`，与前端 `1=正式版,2=测试版,3=内测版,4=候选版` 一致 | 编码语义变更影响存量数据：原 `1` 现按正式版处理，原 `4` 现按候选版处理；上线前需盘点存量 `version_type` |
| 高 | **升级动作返回值存在三种表达** | VO/SDK 为 `Integer action`（`AppVersionUpdateCheckVO.java:34`、`AppUpdateCheckResult.java:28`）；updater 为 `String action` 并用 `asText()` 读取（`UpdateInfo.java:31,75`）；README 示例为 `"FORCE"` 大写（`updater/README.md:190`）；枚举 value 为小写 `force/recommend/notify` | 接入方需确认实际下发格式；建议在服务端固定输出形态，并在 updater 侧做归一化 |
| 中 | **兼容动作枚举注释与实现相反** | 注释“编码值越大强制程度越高”（`AppVersionCompatibilityActionEnum.java:8-9,34`），实际 `FORCE=1` 且实现取最小 code（`AppVersionCompatibilityPolicyServiceImpl.java:180`） | 误导调用方；应修正注释，而非改编码（SQL、SDK、UI 均按 `1=force` 实现） |
| 中 | **版本号缺少单调递增约束** | `validateDuplicateVersionCode()` 仅查重（`AppVersionServiceImpl.java:233-241`） | 可录入更小的 `versionCode`，导致“最新版本”与升级判定异常；建议新增“大于该 appKey+platform 历史最大值”校验 |
| 高 | **主数据限定正式版后的存量数据影响** | `queryLatestReleased()` 现按 `flag=RELEASE` + `versionType=1` 过滤（NULL 兜底）；历史数据中可能存在 `version_type` 为 NULL 或非 1 但已发布的版本 | 这些版本将不再出现在主更新数据；上线前需盘点并修正存量 `version_type`，或在客户端保留旧版本兜底 |
| 中 | **`versionName` 无格式校验** | 仅必填（`AppVersionServiceImpl.java:74-76`） | 展示版本号可任意填写；建议约定格式并校验 |
| 中 | **网关版本占位符文档不一致** | 实际配置为 `@project.app.version@`（`application.yml:58`、POM `project.app.version=1.6`），但 `PublicGatewayVersionController.java:102,109`、`app/README.md:225,345`、`docs/guideline/06:49`、`docs/guideline/04:142` 仍写 `@project.version@`/`app.gateway.version`；根 `README.md:316` 示例仍返回 `1.0-SNAPSHOT` | 排查发布版本问题时容易误判；建议统一文档与示例 |
| 中 | **兼容策略缓存注解不完整** | 仅 `enablePolicy/disablePolicy` 有 `@CacheEvict`（`AppVersionCompatibilityPolicyServiceImpl.java:128-150`），`evaluateCompatibility` 未见 `@Cacheable`，策略增删未见失效注解 | 缓存收益与一致性均不明确；建议要么补全缓存链路，要么移除无效注解 |
| 中 | **兼容策略唯一索引被注释** | `AppVersionCompatibilityPolicyEntity.java:21-22`，因 `source_version_code` 为 NULL 时的数据库兼容性问题 | 可创建重复策略；建议通过应用层校验或改索引结构兜底 |
| 中 | **前端状态筛选缺少归档态** | `VersionList.vue:16-22` 筛选项到 `-2` 为止，但同文件 `59` 行提供归档操作 | 归档版本无法通过筛选查看；建议补充 `ARCHIVED(-3)` |
| 中 | **前端依赖无锁文件且版本口径混乱** | `package.json` 精确版本与 `^` 混用、无 lockfile、`engines.node >=8.9` 与规范 Node 16 不符 | 构建不可复现；建议生成并提交锁文件、统一 Node 版本声明 |
| 低 | **更新器 `local.startScript` 配置无效** | `updater/README.md:160,322` 明确说明；`updater.properties.template:38-39` 仍保留该配置项 | 用户配置后不生效；建议删除模板项或实现该键 |
| 低 | **CI 环境配置遗留** | `app-ui-vue/.travis.yml:2` 为 Node 10，`script: npm run test` 但无 `test` 脚本；06 分册为 Node 16 | 易误触发失败构建；建议清理或更新 |
| 低 | **分支/标签规范未成文** | 仓库实际有 `main/develop/hotfix/springboot3/stable_v1` 与 `v1.4`~`v1.6` 标签，但文档只规定 `main` 与 hotfix，无标签命名/打点规则 | 标签 `v1.6` 与网关版本 `1.6`、Maven `1.0-SNAPSHOT` 三套口径并存；建议成文并明确同步关系 |

## 6. 模块职责划分与相互依赖关系

### 6.1 后端模块

| 模块 | 关键路径 | 职责 | 依赖方向 |
|---|---|---|---|
| `shared-pojo` | `shared/shared-pojo/.../entity/version/`、`.../enums/AppVersion*.java`、`.../criteria/` | 定义版本实体、枚举、查询条件与状态编码 | 依赖 `sql-api` |
| `shared-api` | `shared/shared-api/.../mapper/version/` | 版本/策略/安装包 Mapper 与服务模板契约 | 依赖 `shared-pojo`、`tree-api` |
| `system-api` | `system/system-api/.../service/version/`、`form/`、`vo/` | 版本服务接口、Form/VO 契约 | 继承 `system` 聚合层公共依赖 |
| `default-system-impl` | `system/default-system-impl/.../impl/version/`、`config/BuisnessBeanConfig.java` | 版本 CRUD、状态流转、兼容策略、安装包服务实现与 Bean 装配 | 依赖 `system-api`、`shared-api`、`dic-api`、`logging-api`、`view-route-api`、`oss-api`、`push-api`、`sql-impl` |
| `app` | `app/.../controller/privates/version/`、`.../publics/Public*Version*.java` | 管理端/公开 API、网关版本探针、启动包 | 依赖 `default-system-impl`、`view-route-default-impl` 等 |
| `dynamic-view-route` | `dynamic-view-route/` | 视图路由版本表、全局版本比对、缓存刷新 | 被 `default-system-impl`（`view-route-api`）与 `app`（默认实现）依赖 |
| `updater` | `updater/` | 检查更新、多文件下载、部署脚本、本地版本持久化 | 独立类库，仅 Jackson 传递依赖 |
| `updater-gui` | `updater-gui/` | 更新器 Swing 演示 | 依赖 `updater` |
| `sdk` | `sdk/` | Java 客户端检查更新 + 下载 | 独立类库，OkHttp/Jackson/SLF4J |

### 6.3 依赖与数据流总览

```text
版本管理后台链路：
app-ui-vue --HTTP--> app (Controller)
                      └─> default-system-impl (ServiceImpl)
                            ├─> system-api (接口 / Form / VO)
                            ├─> shared-api (Mapper 契约)
                            │     └─> shared-pojo (实体 / 枚举 / Criteria)
                            ├─> sql-impl / oss-api / view-route-api / push-api
                            └─> app: build-info + /public/gateway/version + viewVersion

客户端升级链路：
updater-gui ──> updater ──HTTP──> /public/app-update/check
sdk / sdk-csharp ──HTTP──> /public/app-update/check + 下载地址
                            ↑
                      AppVersionCompatibilityPolicyServiceImpl
                      （读最新发布版本 + 生效策略 → action + 安装包地址）

工程依赖治理：
根 pom.xml（dependencyManagement + tbs.version + BOM 顺序）
   └─> 所有 Maven 子模块（内部依赖省略 version）
app-ui-vue/package.json（独立版本体系，无锁文件）
dubbo-go-starter / dubbo-db-demo（独立 Go module，不在 Maven 链路内）
```
