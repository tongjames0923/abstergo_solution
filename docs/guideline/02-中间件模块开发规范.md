# 02 - 中间件/工具模块开发规范

> 适用范围：common、sql、cache、async、web、tree-struct、redis-mod、rabbitmq-mod、mq-mod、xxl-job-mod、open-api-starter、logging 等技术能力模块的新增与修改。

## 2.1 模块结构设计

### 2.1.1 api / impl 拆分（强制）

技术型模块必须参照 `system`、`tree-struct`、`cache`、`sql` 的拆分模式，将**契约**与**实现**分离（`sql` 在 api/impl 之外进一步按数据库方言拆出多个后端实现模块）：

```
xxx-mod/
├── pom.xml                  聚合 pom
├── xxx-api/                 契约层：接口、抽象类、模型、常量、注解、Property
│   └── 依赖约束：不得依赖具体中间件客户端（如 redisson、amqp）
└── xxx-impl/                实现层：具体实现、自动配置、资源文件
    └── 依赖约束：依赖 xxx-api + 具体中间件客户端
```

判定标准：

| 内容 | 归属 |
|------|------|
| 接口 `IXxx`、抽象类 `AbstractXxx`、模型/常量/枚举 | api |
| `@ConfigurationProperties` Property 类 | api（契约的一部分） |
| 具体实现类、`@Configuration` 装配类 | impl |
| i18n 资源文件 `messages-{module}.properties` | impl（或产生文案的模块） |

**例外**：单一职责的小型工具模块（如 common）可以不拆分，但对外暴露仍须面向接口编程。

### 2.1.2 包结构约定

以 mq-api（v2）为参照，模块内按职责分包（v2 以版本子包 `v2/` 隔离新一代契约）：

```
com.tbs.{module}/
├── annotation/      @EnableTbs{Feature} 启用注解（厂商模块保留历史名的如 @EnableRabbitMq）
├── constants/       常量（如 MqHeaderConstants）
├── v2/              当前代际契约根包，内部再按子域拆包：
│   ├── core/        核心契约接口与抽象基类（门面/接收段/分发段/记录/抢占）
│   ├── producer/    发送契约 · consume/ 消费者与路由表
│   ├── vo/          数据模型（非持久化 VO）· enums/ 状态枚举
│   ├── exception/   模块专属异常
│   └── impl/        模块内自带的开箱即用/兜底实现（如内存基本实现）
└── config/          自动配置类；config/property/ 配置属性类
```

#### 2.1.2.1 分包粒度与子域拆包（强制，总纲铁律 12）

标准包结构回答"一个模块该有哪些顶层包"，本节回答"包内类多了怎么办、拆到什么粒度合适"。

**拆包时机**（满足其一即必须拆子包）：

1. 包内类数量 ≥ 15 个；
2. 包内出现 ≥ 2 个清晰的职责聚类（例如装配适配类与层级提供类并存、门面契约类与内部实现类混杂）；
3. 同前缀类成组扎堆（如 `XxxConfig`/`XxxProperty`/`XxxProvider`/`XxxDecorator` 各自成群）。

**粒度下限**（防过度拆分）：

1. 子包内类数量 ≥ 3 个（`annotation`、`exception`、`constants` 等天然单一职责的小包除外）；
2. 包层级深度 ≤ 3（自模块根包 `com.tbs.{module}` 起算）；
3. 禁止无语义的单类包与无意义的层级嵌套（如 `internal/core/impl` 三连包套一个类）。

**包名规范**：全小写、单词、语义化，能从包名读出该包的单一职责。

**仓库真实示例**（正反对照，git 历史可查）：

- 正例：`cache-caffeine-impl` 由平铺根包重构为按子域分包——`adapt`（引擎适配）、`level`（多级缓存层级提供者）、
  `config`（装配与配置，内含 `property` 子包），各类归位单一职责包，符合本节全部标准；
- 反例：重构前 `CaffeineAdaptTtlCache`、`CaffeineLevelCacheProvider`、`CaffeineCacheConfig` 等全部类
  平铺在模块根包 `com.tbs.cache.caffeine` 下，职责聚类混杂，即铁律 12 所禁止的"平铺大包"。

### 2.1.3 依赖方向（强制）

```
业务模块(app/system/dic) ──► 模块impl ──► 模块api ──► common/shared
```

- api 模块**禁止**反向依赖 impl 模块。
- impl 之间**禁止**相互依赖造成环；需要协作时通过 api 层接口解耦。
- 业务模块优先依赖 api，仅在启动类/装配时引入 impl。

## 2.2 启用注解与自动装配

### 2.2.1 Enable 注解（强制模式）

每个可独立启用的技术模块提供 `@EnableTbs{Feature}` 注解，通过 `@Import` 导入注册器：

```java
/**
 * 启用 Redis 模块默认装配的注解
 *
 * @author abstergo
 * @since 1.0.0
 */
@Import(RedisPackAutoRegister.class)
@Retention(RetentionPolicy.RUNTIME)
@Inherited
@Target(ElementType.TYPE)
public @interface EnableTbsRedis {
}
```

规则：

1. 注解命名统一 `@EnableTbs{Feature}`（如 `@EnableTbsCache`、`@EnableTbsRedis`、`@EnableSharedLibBean`、`@EnableViewControl`）；历史模块允许保留旧名（rabbitmq-mod 的 `@EnableRabbitMq`）。
2. 注解只做 `@Import`，不写逻辑；装配逻辑集中在 `{Feature}AutoRegister` / `{Feature}Config`。
3. 厂商具体模块的 Enable 注解应包含抽象层的装配范围（如 rabbitmq-impl 的 `RabbitMqAutoRegister` 扫描包含 mq-api 的 `com.tbs.mq`）。
4. 可用 Spring Boot 标准自动装配（`META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`）替代 `@EnableTbs{Feature}`：引入即装配、无需注解（如 sql 与其各方言模块）。此时同职责多实现必须用 `@ConditionalOnMissingBean` 互斥（如各方言 `SqlDialect` Bean 带 `@ConditionalOnMissingBean(SqlDialect.class)`，多方言 jar 并存只装一个）。

### 2.2.2 条件化装配（强制）

所有自动配置 Bean 必须可开关，遵循：

```java
@Configuration
@ConditionalOnProperty(prefix = "tbs.redis", name = "enable", havingValue = "true")
public class BasicRedisConfig {
    // Bean 定义
}
```

1. 开关属性统一 `tbs.{module}.enable`，默认值在 Property 类中声明（建议默认 `false`，由使用方显式开启；框架型基础能力可默认 `true`）。
2. 同一职责的多个可选实现必须**互斥装配**，通过一个属性二选一（参照 `tbs.schedule.embedded-trigger` = `true` 内嵌线程轮询 / `false` 改由外部调度器（如 xxl-job）驱动），**严禁双装配**。
3. 提供默认 Bean 时使用 `@ConditionalOnMissingBean`，允许业务方覆盖。

### 2.2.3 配置属性类（强制）

```java
/**
 * Redis 模块配置属性类
 * <p>
 * 通过@ConfigurationProperties注解绑定tbs.redis前缀的配置属性，
 * 集中管理本模块的可配维度，替代零散的@Value注入。
 * 不使用@Component注册，改由对应 Config 经@EnableConfigurationProperties显式激活，
 * 避免重复导入时重复注册。
 * </p>
 *
 * @author abstergo
 * @since 1.0.0
 */
@Data
@ConfigurationProperties("tbs.redis")
public class RedisProperty {

    /**
     * 模块总开关
     */
    private boolean enable = false;
}
```

规则：

1. 前缀统一 `tbs.{module}(.子域)`。
2. Property 类**不加** `@Component`，由对应 Config 用 `@EnableConfigurationProperties` 显式激活（避免重复注册）。
3. 所有字段必须有默认值与块注释；常量（可选值枚举值）以 `public static final` 声明在类内。
4. **禁止**使用多个 `@Value("${...}")` 读取零散属性；发现即重构收拢。
5. 支持实现类全限定名作为配置值实现"配置驱动切换实现"（参照 `tbs.cache.cache-manager-impl`、`tbs.web.auth.token-issuance-center-impl`）。

## 2.3 模块化国际化（强制）

模块内产生的任何面向用户文案（错误消息、提示），必须走模块化 i18n：

### 2.3.1 资源文件

- 路径：`src/main/resources/i18n/`
- 命名：`messages-{module}.properties`（默认/中文）+ `messages-{module}_en_US.properties`（英文）
- key 风格：`{module}.{domain}.{desc}` 全小写点分（如 `dic.code.empty`、`dic.item.label.exists`）
- 支持占位符：`dic.not.exists=字典 {0} 不存在`

### 2.3.2 注册器

每个模块提供继承 `AbstractMessageSourceProvider` 的 `@Component`：

```java
/**
 * View Route 模块消息源提供者
 *
 * @author abstergo
 */
@Component
public class ViewRouteMessageSourceProvider extends AbstractMessageSourceProvider {

    @Override
    public String getBasename() {
        return "i18n/messages-view-route";
    }

    @Override
    public int getOrder() {
        return -600;
    }
}
```

规则：basename 与资源文件对应；`getOrder()` 决定同名 key 的覆盖优先级，模块间必须错开且注释说明。

### 2.3.3 文案获取

- 断言场景：`AssertUtil...i18n("key")`（推荐，见 03 分册）。
- 直接取文案：`I18nUtil.get("key")`。
- **禁止**在代码里拼接中文/英文字面量作为用户可见消息。

## 2.4 中间件集成层专项规范

### 2.4.1 Redis（redis-mod）

- 数据存取统一经 `IDataHolder` / `RedisDataHolder`，不自建 RedisTemplate 用法。
- 分布式锁统一经 `ILockProvider` / `RedissonLockProvider`，使用模板：`try { tryLock(timeout) ... } finally { if (isHeldByCurrentThread()) unLock() }`。
- 键命名：`domain:type:id` 冒号分层。
- 序列化：生产用 JSON（`GenericJackson2JsonRedisSerializer`）。

### 2.4.2 RabbitMQ（rabbitmq-mod）

- 厂商通道退化为**纯传输层**：业务消费基于 mq-api v2 记录驱动模型，继承 `RabbitMqContext<T>`（自建容器）或 `RabbitMqListenerContext<T>`（`@RabbitListener` 接入），只面向负载 `T`、不感知厂商确认。
- 确认模式必须 `AcknowledgeMode.MANUAL`：**建档成功才 ack**，建档失败才 nak（且**不 requeue**）；失败恢复一律从记录层出发，不依赖厂商重投/死信。
- 交换机/队列/绑定由上下文 `MqResourceDeclarer` 统一声明（`autoDeclare=true`），业务代码禁止重复 declare 造成冲突。
- 发送统一经 v2 契约 `IMqMessageProducer`（`RabbitMqMessageProducer` 落地），以 `MqMessageOutcomeVO` 信封描述 topic/routeKey/payload；禁用厂商 `RabbitTemplate` 直接发送（会丢 messageId/类型头）。
- 消费者**必须幂等**（台账为事后记录，整体重放可能重复投递）；重试语义由 `MqConsumeException.retryFlag` 声明；消息体保持精简。

### 2.4.3 MQ v2 记录驱动链路（mq-mod）职责划分（强制）

| 组件 | 职责 | 禁止事项 |
|------|------|----------|
| `IMqRecorder`（主记录+台账） | 纯存取：`record`/`updateFlag`/`errorFlag`/`recordConsume`/`get` + 记录层事务 | 禁止内嵌重试扫描/定时调度/分发逻辑 |
| `IMqMessageReceiver` / `IMqMessageProcessor` | 接收段（组装·校验·建档·ack/nak 回调）/ 分发段（按负载类型广播、构台账行） | 禁止跨段越位；接收段不持有厂商类型，确认由 `SConsumer` 回调注入 |
| `IMqContext`/`AbstractMqContext` | 装配门面：待处理队列 + 处理线程 + 生命周期 | 禁止将业务消费逻辑上提至门面 |
| 重试扫描/回灌 | 独立外部组件（读 FAILED 主记录/FAIL 台账行回灌）——尚未落地 | 禁止于记录层内嵌定时；与存储层解耦 |

> 内存基本实现（`com.tbs.mq.v2.impl`）仅供单机/开发/自检；集群与持久化应换用 `redis-mod` 的 `com.tbs.redis.mq`（`RedisMqRecorder` / `RedisMqMessageMonopolizer`，已落地），DB 记录器仍为待闭环项（见 [mq-v2 设计大纲 §7.2](../mq-v2-design-outline.md)）。

### 2.4.4 XXL-Job（xxl-job-mod）

- 新增定时任务优先实现 `IJsonJobHandler<T>`，经 `jsonJobHandler` 统一入口以 JSON 参数触发，避免每个任务注册独立 handler。
- 参数类为普通 POJO，必须可被 FastJSON2 反序列化。
- `IXXLJobsConfig` 由应用侧提供 Bean；`adminAddress` 必填，其余走默认值。

## 2.5 扩展点设计原则

1. **面向接口**：每个可替换能力定义 `I{Name}` 接口 + 可选 `Abstract{Name}` 骨架实现（模板方法），实现类命名 `{Impl}{Name}`。
2. **配置驱动替换**：Property 中持有实现类 Class 字段，装配时按类名实例化（参照 `BeanUtil.buildBeanFromProperties` 用法）。
3. **兜底实现**：框架必须提供 Noop/内存兜底实现（如 `NoopFailedMessageStore`、`MapDataHolder`），保证未配置外部中间件时可启动。
4. **启动任务**：需要启动后初始化的逻辑实现 `IStartup`，通过 `getOrder()` 控制顺序。

## 2.6 新模块开发流程（Checklist）

1. 确认是否需要新模块：能在现有模块加扩展点解决的，不新建模块。
2. 按 2.1 建 api/impl 子模块与包结构，登记到聚合 pom。
3. 编写 Property 类 + Config 条件装配 + `@EnableTbs{Feature}` 注解。
4. 定义契约接口与抽象基类，提供兜底实现。
5. 添加 `messages-{module}.properties`（中英）+ MessageSourceProvider。
6. 编写模块 README（结构参照现有模块：概述/快速开始/配置说明/核心组件/最佳实践/故障排除）。
7. 对照 [07-Code Review 检查清单](07-Code-Review检查清单.md) 自检。

## 2.7 工具类使用规范（强制）

| 能力 | 统一入口 | 禁止直接 import |
|------|----------|----------------|
| 字符串 | `com.tbs.common.util.base.StrUtil` | `cn.hutool.core.util.StrUtil` |
| 集合 | `com.tbs.common.util.base.CollUtil` | `cn.hutool.core.collection.CollUtil` |
| Bean | `com.tbs.common.util.base.BeanUtil` | `cn.hutool.core.bean.BeanUtil` / `cn.hutool.core.bean.copier.CopyOptions` |
| Spring | `com.tbs.common.util.framework.SpringUtil` | `cn.hutool.extra.spring.SpringUtil` |
| 日期时间 | `com.tbs.common.util.time.TimeUtil` | `cn.hutool.core.date.**` |

1. **统一入口**：上表能力一律使用项目封装，业务代码禁止直接 import Hutool 原始类；存量代码按本节逐步迁移。
2. **类型边界**：对外方法签名、返回值与 DTO 字段不得出现 Hutool 特有类型（`DateTime`、`DateUnit`、`DateField`、`DatePattern` 等）；日期时间一律返回 JDK `Date` / `LocalDateTime` / `LocalDate` / `long` / `String`。
3. **语义核对**：项目封装可能重写 Hutool 方法语义（如项目 `StrUtil.format` 采用 `{0}` 占位符，Hutool 原版为 `{}`），迁移时须逐处核对，禁止机械替换 import。
4. **未覆盖能力**：表中未覆盖的 Hutool 能力（如 `CsvReader` / `CsvWriter`、`ResourceUtil`）暂允许在框架模块内部直接使用，但不得让 Hutool 类型穿透到对外契约；新增使用前先确认是否已有项目封装。
