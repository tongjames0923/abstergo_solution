# 03 - 功能模块开发规范

> 适用范围：业务功能开发（app 主应用、system、dic、dynamic-view-route 等业务模块），覆盖从实体到控制器的完整后端开发链路。
> 开发语言：**统一使用 Java**。项目已全面 Java 化（dic-service 存量 Kotlin 已重写为 Java），禁止新增 Kotlin 代码与 Kotlin 依赖。

## 3.1 分层架构与职责

```
Controller（app/controller/privates|publics）
   │  仅做：HTTP 接入、参数组装（Form→Entity）、调用服务层、包装 AjaxResult
   ▼
Service（业务模块 service/impl）
   │  业务规则校验（AssertUtil）、业务编排、事务、缓存、数据访问
   ▼
Mapper（MyBatis） + QueryEngine（自研 sql 框架）
   ▼
Entity（shared-pojo 或业务 api 模块）
```

**强制职责划分**：

| 层 | 允许 | 禁止 |
|----|------|------|
| Controller | 参数兜底默认值、Form↔Entity 简单组装、调用服务、返回 AjaxResult | 业务校验（判空存在性、重复性、状态规则）、直接访问 Mapper、写业务逻辑 |
| Service | 全部业务规则校验与逻辑、事务边界、缓存注解 | 感知 HTTP（request/response）、返回 AjaxResult |
| Mapper/QueryEngine | 数据存取 | 业务判断 |

## 3.2 实体（Entity）规范

```java
/**
 * 系统数据字典实体
 *
 * @author abstergo
 * @since 1.0.0
 */
@Entity
@Table(name = "sys_data_dic",
    indexes = {@Index(name = "idx_data_dic_name_code", columnList = "data_dic_name,data_dic_code"),
        @Index(name = "idx_flag", columnList = "flag")})
@Data
@AllArgsConstructor
@NoArgsConstructor
@LogicDeleteEntity(filedName = "flag", activeFlagValues = {1, -1})
public class SystemDataDicEntity implements IBaseEntity<Long> {

    private static final long serialVersionUID = 1L;

    @Id
    @SqlAutoValue(value = IdAutoProvider.class, insertOnly = true)
    private Long id;

    /**
     * 数据字典编码
     */
    @Column(name = "data_dic_code")
    private String dataDicCode;

    /**
     * 状态
     *
     * @see com.tbs.dic.enums.DataDicFlagEnum
     */
    @Column(name = "flag")
    private Integer flag;
}
```

规则：

1. 必须实现 `IBaseEntity<Long>`（ID 类型统一 Long，主键由应用侧雪花生成，不使用 `@GeneratedValue`）。
2. Lombok `@Data` + `@AllArgsConstructor` + `@NoArgsConstructor`；声明 `serialVersionUID`。
3. 表名用业务前缀（`sys_` 系统域）；字段名蛇形命名，实体字段驼峰，显式 `@Column` 映射。
   列名与表名的推导规则与 Hibernate 完全一致：显式 `@Column(name)` / `@Table(name)` 优先，未声明时按驼峰转下划线（`createTime` → `create_time`）。显式声明仍是硬要求，fallback 只是防止漏写时运行期 SQL 与建表结构偏差。
4. 索引一律**由查询驱动**，且**只能通过 `@Table(indexes = ...)` 注解声明**：只声明确实被某条查询用到的索引，写不出查询依据就不建，能合并的必须合并；
   建表脚本按注解同步，状态类字段保留单列索引，禁止唯一索引（见 3.3.4）。
5. **逻辑删除优先**：需要删除语义的实体使用 flag 字段 + `@LogicDeleteEntity`，flag 含义用对应 `XxxFlagEnum` 枚举（实现 `BaseEnum`）并在字段注释 `@see` 引用；物理删除仅限日志类/关系表等场景。
6. 时间字段 `createTime`/`updateTime`（`Date` 类型）；自动填充用 `@AutoSetDate`（更新场景加 `onUpdate = true`）。
7. 实体放置：跨服务共享实体放共享/业务 api 模块（如 shared-pojo、dic-api）；应用私有实体放应用模块。
8. **只声明索引，不声明约束**：`@Table` 只用 `indexes = @Index(...)` 描述查询加速；
   **禁止** `uniqueConstraints`，**禁止** `@Column(nullable = false)` / `columnDefinition` 默认值 / `@JoinColumn` 外键。
   唯一性、非空、默认值均由 Service 层断言表达，详见 3.3.3。
9. **继承边界：不要为“少写几个字段”抽实体基类**。
   - 表名只存在于最终实体上，不会出现父类一张表、子类另一张表的情况；`@Table` 一律写在最终实体
   - 元数据侧（SELECT / INSERT / UPDATE 的列）会识别父类字段，`@Id` 写在父类也能识别
   - DSL 侧（`Entity::getXxx`）只能引用实体**自身声明**的字段：`LambdaUtil.getField` 用 `getDeclaredField` 查找，
     引用继承字段会在解析阶段直接报“释放字段异常”。即：继承字段能读写，但不能做条件与排序
   - 共享行为用接口表达（如 `IBaseEntity<Long>`，不带字段），不要用带字段的基类

## 3.3 数据访问规范

数据层只有一套：**Hibernate 负责建表，自研 sql 框架负责全部读写**，`jakarta.persistence` 注解是两边共用的唯一元数据真源。

### 3.3.1 查询：优先 QueryEngine（自研 sql 框架）

```java
/* 单条查询 */
SystemDataDicEntity entity = QueryEngine.getEntityQueryWrapper(dicEntity)
    .query().where()
    .equal(SystemDataDicEntity::getDataDicCode, code)
    .pour().fetchOne();

/* 列表 + 排序过滤 */
List<SystemDataDicItemEntity> items = QueryEngine.getEntityQueryWrapper(dicItemEntity)
    .query().where()
    .equal(SystemDataDicItemEntity::getDicCode, dicCode)
    .pour().fetch();
```

1. 条件查询优先用链式 wrapper（`equal/leftLike/in/greaterEqual...` + `pour()` 结束条件段 + `fetch()/fetchOne()`）。
2. 复用型查询场景可定义 Query 类（继承 `ClassBaseQueryCriteria<T>`，字段标注 `@QueryMapping` + `@QueryField`），参照 sql 模块 README。
3. 复杂 JOIN / 跨表查询优先用 `AbstractResourceCriteria` 从 classpath SQL 文件加载（SQL 外置、按库型维护），或在该 Mapper 上写专用 `@Select` 方法；
   `@SelectSQL` 可标在查询模型**类上**作为简短固定 SQL，但框架会在其后追加 WHERE（含逻辑删除与数据权限条件），
   因此 SQL 内**不得自带 WHERE**，且列投影对它无效。
4. 分页统一走框架 `getPageSupport()` / `PageUtil`，禁止手写 limit 拼接。
5. **禁止**字符串拼接 SQL；禁止绕过框架直接 new JdbcTemplate。

### 3.3.2 Mapper（GenericMapper）

- 业务 Mapper 继承 `IFrameworkMapper<T, K>`，放业务 api 模块 `mapper/` 包（如 `DataDicMapper`），供服务实现注入。
- 分工：单表增删改查用继承来的 `insert/insertSelective/updateByPrimaryKey/updateByPrimaryKeySelective/deleteByPrimaryKey/selectByPrimaryKey`；
  带业务条件的查询走 QueryEngine。

**硬规则**

1. **逻辑删除实体禁止走 GenericMapper 的条件方法**（`select` / `selectCount` / `delete`）。
   这三个方法只按实体非空字段拼条件，**不注入逻辑删除的 flag 过滤**：`select` 会把已删除数据原样查回来，
   `delete` 会把逻辑删除做成物理删除。这类实体的读写一律走 QueryEngine，由 `SqlLogicDeleteIntercepter` 自动补
   `flag IN (...)` 条件。
2. **需要整体回滚的批量写必须包事务**。`insertList` / `deleteByIdList` 按方言上限拆成多次执行（SQL Server 1000 行、
   Oracle 1000 项），**不是原子操作**，中途失败会留下已提交的前几批数据；这类场景调用方加
   `@Transactional(rollbackFor = Exception.class)`。这是适配上限的必要代价，不接受把批次合并回单条 SQL。
   **例外（已确认口径）**：业务上明确容忍部分成功的批量写入（操作日志落库、埋点、统计上报等）可**不加事务**——
   包成整体事务反而会让一条脏数据把整批数据回滚掉，放大失败半径；但必须在写入处用块注释写明「有意不做整体回滚」的理由，
   否则评审按未加事务打回。参照 `LoggingRecordConsumer#flushBuffer()`。
3. **单批方法禁止业务直调**：`insertBatch` / `selectByIdListBatch` / `deleteByIdListBatch` 只供分批方法内部使用，
   传入空集合会中断执行（避免生成 `IN ()` / `VALUES ()` 坏 SQL）。
4. **条件语义**：`select` / `selectCount` / `delete` 只拼接“非 null、非空串、且非集合/数组”的字段，
   全部为空时退化为无 WHERE 的全表语句；`insertSelective` / `updateByPrimaryKeySelective` 只跳过 null，
   空串会被写入。
5. **列名与别名**：SELECT 统一生成 `列名 AS 属性名`，因此 `@Column` 列名与 Java 属性名不一致时（如 `prop_value` → `value`）
   也能正确映射；别名是显式覆盖，`map-underscore-to-camel-case` 只是手写 SQL 的兜底。

### 3.3.3 不依赖数据库能力（强制）

数据库只负责**存放数据**与**加速查询**，不承担任何业务规则（总纲铁律 14）。

存量表不追溯：既有表上的 `UNIQUE KEY`、`NOT NULL`、`DEFAULT`、外键等保持不变，按存量遗留逐步治理；
但**新增表、新增列、以及新增写入路径不得再引入**。

#### 禁止与替代对照

| 数据库能力 | 禁止的用法 | 业务层替代写法 |
|---|---|---|
| 唯一约束 | `UNIQUE KEY`、`@UniqueConstraint` | 写入前按键判存，`AssertUtil` 断言拒绝重复；DB 只建普通索引 |
| 非空约束 | `NOT NULL`、`@Column(nullable = false)` | Service 层断言必填，列一律允许为空 |
| 默认值 | `DEFAULT`、`columnDefinition` | 业务代码显式赋值；配置类默认值放 Property 字段 |
| 外键 | `FOREIGN KEY`、`@JoinColumn` | 断言关联对象存在；删除时业务层显式清理关联行 |
| 级联删除 | `ON DELETE CASCADE/UPDATE` | 业务层按依赖顺序显式删除，逻辑删除优先 |
| 状态合法性 | `CHECK`、枚举列、触发器 | 状态流转判定放在 Service |

#### 唯一性写法

```java
/* 写入前判存，拒绝而非覆盖 */
AssertUtil.isTrue(existsByCode(form.getDicCode()))
    .i18n("dic.code.exists")
    .params(form.getDicCode())
    .errorLevel(ErrorLevelEnum.USER_INPUT_ERROR)
    .throwIt();
mapper.insert(entity);
```

拒绝而非更新的原因：覆盖会静默改写已有记录的业务字段（状态、归属、时间），把上游的调用时机错误掩盖成一条成功日志。

#### 读路径配套

去掉唯一约束后，同键多行在理论上可能出现。查询这类键时必须显式排序取首行，并保证**读路径与写入路径命中同一行**：

```java
var wrapper = QueryEngine.getEntityQueryWrapper(entity);
wrapper.where().equal(Entity::getToken, token);
wrapper.getOrderSupport().ifPresent(order -> order.orderByDesc(Entity::getCreateTime));
return wrapper.fetchOne();
```

#### 并发说明

先查后写在并发下会穿透，这是本规则的已知代价。需要强唯一保证的场景由业务层自行承担：

- 优先用**幂等键**（业务唯一标识 + 状态），重复提交自然收敛为同一结果；
- 必须串行化的场景用项目已有的分布式锁（`redis-mod`）；
- **不得**回头加数据库唯一约束作为兜底，一旦加回则本规则失效。

拿这个代价换取的收益：规则随代码走、可单测、可被 RPC 层复用；不因库型（MySQL/SQLServer/PG）差异而产生行为差异；新增规则不需要 DDL 窗口与锁表。

### 3.3.4 索引必须来自查询（强制）

索引只有一个来源：**已经存在的查询**。先有 `WHERE` / `ORDER BY`，后有 `@Index`；
**禁止**「这个字段看着像查询条件」「以后可能要用」的预防性索引（总纲铁律 15）。

#### 声明入口唯一：实体 `@Table` 注解

1. 索引**只能写在实体 `@Table(indexes = {@Index(...)})` 上**，这是全项目唯一的索引声明入口；
   `etc/sql_file/` 建表脚本只是按注解同步出来的产物，**禁止**出现注解里没有的索引，
   也**禁止**绕过注解在手写 DDL（`CREATE INDEX` / `ALTER TABLE ... ADD KEY`）里加索引——
   绕开注解的索引在下一个环境（另一库型、重建表）里不存在，是隐性结构偏差。
2. **禁止任何唯一索引**：`@Index(unique = true)`、脚本里的 `UNIQUE KEY` / `CREATE UNIQUE INDEX` 一律不得出现。
   唯一索引会让数据库替业务判重：重复键直接抛库级异常，业务层拿不到可读错误、也走不到 `AssertUtil` 分支，
   等于把部分业务逻辑挖进了库里（铁律 14）。判重一律走「写入前查 + 断言」，DB 侧只建普通索引。

#### 每条索引都要有查询依据

新增或修改任一索引（注解与同步出来的脚本）时，必须能指出**至少一处真实使用它的查询**：

| 依据形式 | 举例 |
|---|---|
| QueryEngine 链式条件 / 排序 | `where().equal(Entity::getDicCode, dicCode)` → `idx_dic_code(dic_code)` |
| Query 类 `@QueryField` + `@QueryMapping` 映射出的过滤与排序列 | 列表页按创建时间倒序翻页 → `idx_receiver_create_time(receiver,create_time)` |
| Mapper 专用 `@Select` 或 `AbstractResourceCriteria` 外置 SQL 里的过滤/排序列 | `WHERE app_id=? ORDER BY create_time DESC` → `idx_app_id_create_time(...)` |
| 写入前判存查询（见 3.3.3） | `existsByCode` 按编码判存 → `idx_data_dic_name_code(data_dic_name,data_dic_code)` |

1. 指不出查询 = 不建。评审证据是「文件 + 方法/SQL」，写不出来即打回，不接受「性能优化」「万一要查」这类理由。
2. **索引与查询同生命周期**：某条查询被删除或改掉过滤列时，只被它用到的那条索引要一并复核；
   但回收动作按下面「改实体结构与改查询必须复审索引」的增量原则走，**删除索引只能给建议**。
3. 主键不在此列：`@Id` 是行定位与框架读写的基础，无论是否有条件查询都必须存在。

#### 状态类字段要有独立索引

`flag` / `type` / `status` 这类状态列**必须建单列索引**（如 `idx_flag(flag)`），不得以「区分度低、优化器多半不用」为理由省掉：

1. 逻辑删除与状态筛选是全项目的公共过滤条件，列表、统计、判存几乎都带它，本身就是切实的查询需求；
2. 它**不属于**被联合索引最左前缀覆盖的冗余索引——状态列通常不在联合索引最左位，
   业务列在前、状态列在后的联合索引覆盖不到「只按状态查」这类访问路径；
3. 参照 `dic-api` 的 `SystemDataDicEntity`：`idx_data_dic_name_code(data_dic_name,data_dic_code)`
   与 `idx_flag(flag)` **并存**，不算重复索引。

#### 能合并的一律合并

一张表的索引数量按**访问路径数量**算，不按条件字段数量算：

1. **最左前缀覆盖**：已有 `idx_a_b(a,b)` 时不再单建 `idx_a(a)`；只有确实存在只带 `b` 而不带 `a` 的查询，才另建 `idx_b(b)`。
2. **等值列在前、范围与排序列在后**：`WHERE status=? AND create_time>=? ORDER BY create_time DESC` 建一条
   `idx_status_create_time(status,create_time)` 即可，不再另建 `idx_status` 与 `idx_create_time`。
3. **列顺序只留一套**：`(a,b)` 与 `(b,a)` 是两条不同索引，除非两种访问路径都有真实查询，否则统一成业务条件优先的列在前，不两头建。
4. **语义重复的不建**：同组列换个索引名再建一条、或两条索引的列完全相同仅顺序无关的写法，都算重复。

#### 小表不豁免

表小不是省索引的理由：数据量会随时间增长，而执行计划只在上线后才暴露问题；同一张表按同一规则建索引，
环境之间行为才一致。小表同样按访问路径建——通常 1~2 条即可，不多建也不少建。

#### 不建索引的场景

- 只在主键定位后于内存里判断的字段，以及仅用于人工排查数据方便的列；
- 为「唯一性兜底」建的索引与唯一索引——唯一性走 `AssertUtil` 断言（3.3.3），DB 侧只按查询需要建普通索引。

#### 改实体结构与改查询必须复审索引（强制）

每次修改实体结构（加列、改列、改 `@LogicDeleteEntity` 配置）或查询语句（新增/改写 WHERE、ORDER BY、分页排序）时，
必须**回头重新校验这张表的索引集合**是否与查询对齐：漏索引与空索引都算结构偏差，不得只改代码不看索引。

索引调整以**增量更新为主**：

1. **新增索引**：注解补一个 `@Index` + 脚本补一条 `CREATE INDEX` / `ALTER TABLE ... ADD KEY`（按库型），
   已存量环境靠增量脚本追平；
2. **合并索引**：先建新的联合索引并把查询切过去，旧索引转为废弃建议，不在同一次变更里推倒重建；
3. **删除索引只能给建议**：代码与 SQL 脚本里都**不得主动 DROP 已有索引**，
   在 MR 描述中列出「建议废弃 + 依据（哪条查询已不存在、何时确认无引用）」，由开发者确认环境后手工执行。

只给建议不直接删的原因：索引删除是不可逆的性能回退点，而且线上真实查询未必全部在业务代码里（报表、临时查库、下游服务），
改不到代码的那部分引用只能靠人来确认。

## 3.4 Service 规范

### 3.4.1 服务模板体系

标准 CRUD 业务继承 shared-api 模板，按删除策略选择：

| 模板 | 场景 |
|------|------|
| `AbstractLogicDeleteFullFeatureServiceTemplate` | 逻辑删除的完整 CRUD（默认首选） |
| `AbstractPhysicDeleteFullFeatureServiceTemplate` | 物理删除场景 |
| `AbstractTreeStructService` | 树形结构业务（配合 tree-struct） |
| `AbstractAuditService` | 需要操作审计 |
| `AbstractService` | 非 CRUD 的通用基类 |

模板要求实现 `getMapper()` 与 `newEntity()`；继承后仅覆写需要定制的方法。

### 3.4.2 断言与异常（强制）

所有业务校验使用 `AssertUtil` 链式断言，**这是本项目最高频的规范点**：

```java
AssertUtil.isTrue(StrUtil.isEmpty(dic.getDataDicCode()))
    .i18n("dic.code.empty")
    .errorLevel(ErrorLevelEnum.USER_INPUT_ERROR)
    .throwIt();

AssertUtil.isTrue(old == null)
    .i18n("dic.not.exists")
    .params(dicCode)
    .errorLevel(ErrorLevelEnum.USER_INPUT_ERROR)
    .throwIt();

AssertUtil.isTrue(item != null)
    .i18n("dic.has.undeleted.items")
    .params(dicCode)
    .errorLevel(ErrorLevelEnum.BUSINESS_LOGIC_ERROR)
    .throwIt();
```

规则：

1. 格式：`AssertUtil.{断言方法}(条件).i18n("资源key").params(占位参数...).errorLevel(级别).throwIt()`。
2. **必须** `.i18n(key)`，**禁止** `.message(...)`、禁止 `.message(I18nUtil.get(key))` 组合。
3. key 必须已存在于对应模块 `messages-{module}.properties`（中英文两份都要加）。
4. 错误级别语义：`USER_INPUT_ERROR`（入参问题）/ `BUSINESS_LOGIC_ERROR`(业务规则冲突) / `SYSTEM_ERROR` / `CRITICAL_SYSTEM_ERROR`。
5. 禁止直接 `throw new FormattedRuntimeException(...)`、`throw new RuntimeException(...)`。
6. 捕获系统异常需包装时用 `ExceptionUtil.newException(e, ...)`。

### 3.4.3 缓存

读多写少的数据用 Spring Cache 注解，**`cacheNames` 一律引用模块内的 `CacheNamesConstants` 常量，注解里禁止出现字面量字符串**（总纲铁律 13）：

```java
/**
 * 缓存名称常量
 * <p>
 * 集中管理本模块 Spring Caching 注解使用的 cacheNames，禁止在注解中硬编码魔法值字符串。
 * </p>
 *
 * @see com.tbs.cache.config.TbsCacheProperty.TtlConfig#getOverrides() 对应 TTL 覆盖 key 需与本类取值保持一致
 */
public final class CacheNamesConstants {

    /**
     * 数据字典缓存（按字典编码）
     */
    public static final String DATA_DIC = "data_dic";

    private CacheNamesConstants() {
    }
}

/* 读：只引用常量 */
@Cacheable(cacheNames = CacheNamesConstants.DATA_DIC, key = "#code")

/* 写：失效同一个常量，key 语义与读一致，可带 condition 防空指针 */
@CacheEvict(cacheNames = CacheNamesConstants.DATA_DIC, key = "#dic.dataDicCode",
    condition = "#dic != null && #dic.dataDicCode != null")
```

1. 常量名按缓存用途命名（`UPPER_SNAKE`）且表意明确；**取值**用蛇形小写下划线（如 `data_dic`），
   跨模块可能重名时带 `{module}:` 前缀（如 `app:system_user`）；取值只有常量这一处来源。
2. TTL 等按名称覆盖的策略（`TbsCacheProperty.TtlConfig.overrides`）其 key 必须与常量取值完全一致，
   因此改取值等于改缓存空间，需要连带处理失效与存量数据。
3. **读写成对**：`@Cacheable` 必须有对应 `@CacheEvict`，两处引用同一个常量、key 语义一致；
   写路径多条入口（保存/删除/状态变更）都要各自失效。
4. 参照实现：`WecomApiClient`（`WECOM_ACCESS_TOKEN`）、`SimpleDepartmentUserRelationService`（`USER_DEPARTMENTS`）、
   `GenericApiServiceImpl`（`GENERIC_API`，写路径统一 `allEntries = true`）。
5. key 用 SpEL 引用方法参数（如 `#code`、`#dic.dataDicCode`），常量只负责缓存名称。
6. 缓存管理器已全局配置为 Redisson（`RedissonSpringCacheManager`），模块内不得自建。

### 3.4.4 事务

- 写操作多步持久化加 `@Transactional(rollbackFor = Exception.class)`。
- 事务方法内禁止调用远程 RPC/MQ 发送等不可回滚操作；必须时先落库后异步。

## 3.5 Dubbo 服务规范

跨服务调用统一 Dubbo（**禁止**自建 HTTP 调用替代）：

```java
/* 服务提供方（dic-service） */
@DubboService
public class DataDicServiceImpl implements IDataDicService { ... }

/* 服务消费方（app） */
@DubboReference(lazy = true)
private IDataDicService dataDicService;
```

规则：

1. 服务接口定义在 api 模块（如 `dic-api` 的 `IDataDicService`），接口方法参数/返回值必须可序列化（实体、Model、基本类型、集合）。
2. 消费端引用加 `lazy = true`，避免启动时强依赖提供方。
3. 服务实现内同样遵守 3.4 断言规范；异常会随 RPC 传播，消息已经 i18n 化可直接展示。
4. 远程用户/公司信息查询走 system-api 的 `IUserRemoteService`/`ICompanyRemoteService` 等既有接口，不重复造轮子。

## 3.6 Form / VO / Model 规范

| 类型 | 命名 | 位置 | 要求 |
|------|------|------|------|
| 入参表单 | `{Biz}Form`、`{Biz}SearchForm`、`{Biz}SaveForm` | app 模块 `form/` 包（或 system-api 跨服务表单） | 实现 `Serializable` + `serialVersionUID`；`@Data`；每个字段 `@Schema(description = ...)` 必填项标 `requiredMode = REQUIRED` |
| 出参视图 | `{Biz}VO` | `vo/` 包 | 面向展示裁剪字段，禁止直接外泄实体敏感字段（密码、token） |
| 服务模型 | `{Biz}Model` | 业务 api 模块 `model/` 包 | Dubbo 跨服务传输载体，实现 `Serializable` |

Form 示例：

```java
/**
 * 数据字典保存表单
 *
 * @author abstergo
 * @since 1.0.0
 */
@Data
@Schema(description = "数据字典保存表单")
public class DicSaveForm implements Serializable {
    private static final long serialVersionUID = 1L;

    /**
     * 字典编码
     */
    @Schema(description = "字典编码", requiredMode = Schema.RequiredMode.REQUIRED)
    private String dicCode;
}
```

## 3.8 新功能开发标准流程

以"新增一个业务管理功能"为例的完整步骤：

1. **建模**：先列出这张表会被哪些查询访问（WHERE/ORDER BY 清单），设计表结构（只建主键与普通索引，不建唯一/非空/默认值/外键等约束，见 3.3.3）→ 实体（api/shared-pojo 模块）+ FlagEnum + 按查询反推的索引声明（只写注解，见 3.3.4）；SQL 脚本按注解同步更新到 `etc/sql_file/`。
2. **Mapper**：api 模块新增 Mapper 接口。
3. **服务**：定义 `I{Biz}Service` 接口（api 模块）→ 实现类继承服务模板，业务校验全部用 AssertUtil + i18n key。
4. **i18n**：新增的 key 同步写入模块 `messages-{module}.properties` 中英文文件。
5. **控制器**：app 模块 `controller/privates` 新增 Controller（见 04 分册）。
6. **Dubbo**（如独立服务）：提供方 `@DubboService`，消费方 `@DubboReference(lazy = true)`。
7. **前端对接**：按 04/05 分册完成接口联调与页面开发。
8. **自检**：对照 07 检查清单逐项核查；本次改动涉及实体结构或查询语句的，同步复审该表索引集合与增量脚本（见 3.3.4，删除索引只写建议）。校验范围以「静态检查 + `mvn compile` 编译通过」为上限（总纲「AI 辅助开发使用说明」5）；
   启动、Dubbo/接口联调、页面实机验证由开发者本人在环境完成，**不为此新增单元测试/集成测试代码**（除非用户明确要求）。

## 3.9 方法改造与弃用规范（向前兼容）

改造或重构**公共契约方法**（api 模块契约接口、Dubbo 服务接口、对外暴露的 Service 接口等多方依赖的方法）时，**禁止直接修改原方法签名或语义**，
必须走「新增方法 + 弃用旧方法」的渐进迁移模式，保持向前兼容，让调用方按自己节奏缓慢迁移。

### 3.9.1 标准步骤

1. 在同一接口声明下新增一个承载新逻辑的方法（同名重载或语义更清晰的新名称）。
2. 旧方法保留并继续可用，可内部委托到新方法实现，避免两套逻辑分叉。
3. 旧方法标注 `@Deprecated` 注解，并在块注释中用 `@deprecated` 注明**替代方法**与**计划移除版本**。
4. 迁移期内旧方法行为不变、不删除；到达移除版本且确认无调用方后再统一清理。

示例：

```java
public interface IDataDicService {

    /**
     * 按编码查询数据字典
     *
     * @param dicCode 字典编码
     * @return 字典实体
     * @deprecated 自 1.1.0 起弃用，请使用 {@link #getDicByCode(String, boolean)} 替代，计划于 2.0.0 移除
     */
    @Deprecated
    SystemDataDicEntity getDicByCode(String dicCode);

    /**
     * 按编码查询数据字典（支持是否包含已逻辑删除数据）
     *
     * @param dicCode 字典编码
     * @param includeDeleted 是否包含已逻辑删除的数据
     * @return 字典实体
     */
    SystemDataDicEntity getDicByCode(String dicCode, boolean includeDeleted);
}
```

### 3.9.2 规则与例外

1. **适用范围**：仅限多方依赖的公共契约方法（api 模块接口、Dubbo 接口、对外 Service 接口）；模块内部私有方法不受此约束，可直接重构。
2. **弃用写法**：`@Deprecated` 注解与块注释 `@deprecated` 必须同时具备，注释中缺一不可地注明替代方法与计划移除版本。
3. **禁止行为**：迁移期内禁止修改旧方法行为、禁止直接删除仍有调用方的公共方法、禁止在旧方法中抛异常逼迫调用方迁移。
4. **例外场景**（可直接修改或删除，不走弃用流程）：
   - 旧方法存在安全漏洞或严重缺陷，必须立即下线；
   - 已确认所有调用方在同一次变更中全量切换完毕（需在 MR 描述中列出全部调用方与切换情况）。
5. 例外场景的变更必须在 MR 描述中显式说明理由，评审人重点核查。
