# 03 - 功能模块开发规范

> 适用范围：业务功能开发（app 主应用、system、dic、dynamic-view-route 等业务模块），覆盖从实体到控制器的完整后端开发链路。
> 开发语言：**统一使用 Java**。存量 Kotlin 实现（如 dic-service 的 DataDicServiceImpl.kt）仅作维护，新代码不得新增 Kotlin。

## 3.1 分层架构与职责

```
Controller（app/controller/privates|publics）
   │  仅做：HTTP 接入、参数组装（Form→Entity）、调用服务层、包装 AjaxResult
   ▼
Service（业务模块 service/impl）
   │  业务规则校验（AssertUtil）、业务编排、事务、缓存、数据访问
   ▼
Mapper（MyBatis） + QueryEngine（自研 sql 框架）
   ▼
Entity（shared-pojo 或业务 api 模块）
```

**强制职责划分**：

| 层 | 允许 | 禁止 |
|----|------|------|
| Controller | 参数兜底默认值、Form↔Entity 简单组装、调用服务、返回 AjaxResult | 业务校验（判空存在性、重复性、状态规则）、直接访问 Mapper、写业务逻辑 |
| Service | 全部业务规则校验与逻辑、事务边界、缓存注解 | 感知 HTTP（request/response）、返回 AjaxResult |
| Mapper/QueryEngine | 数据存取 | 业务判断 |

## 3.2 实体（Entity）规范

```java
/**
 * 系统数据字典实体
 *
 * @author abstergo
 * @since 1.0.0
 */
@Entity
@Table(name = "sys_data_dic",
    indexes = {@Index(name = "idx_data_dic_name_code", columnList = "data_dic_name,data_dic_code"),
        @Index(name = "idx_flag", columnList = "flag")})
@Data
@AllArgsConstructor
@NoArgsConstructor
@LogicDeleteEntity(filedName = "flag", activeFlagValues = {1, -1})
public class SystemDataDicEntity implements IBaseEntity<Long> {

    private static final long serialVersionUID = 1L;

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    /**
     * 数据字典编码
     */
    @Column(name = "data_dic_code")
    private String dataDicCode;

    /**
     * 状态
     *
     * @see com.tbs.dic.enums.DataDicFlagEnum
     */
    @Column(name = "flag")
    private Integer flag;
}
```

规则：

1. 必须实现 `IBaseEntity<Long>`（ID 类型统一 Long，自增主键）。
2. Lombok `@Data` + `@AllArgsConstructor` + `@NoArgsConstructor`；声明 `serialVersionUID`。
3. 表名用业务前缀（`sys_` 系统域）；字段名蛇形命名，实体字段驼峰，显式 `@Column` 映射。
4. 常用查询字段必须在 `@Table(indexes = ...)` 声明索引。
5. **逻辑删除优先**：需要删除语义的实体使用 flag 字段 + `@LogicDeleteEntity`，flag 含义用对应 `XxxFlagEnum` 枚举（实现 `BaseEnum`）并在字段注释 `@see` 引用；物理删除仅限日志类/关系表等场景。
6. 时间字段 `createTime`/`updateTime`（`Date` 类型）；自动填充用 `@AutoSetDate`（更新场景加 `onUpdate = true`）。
7. 实体放置：跨服务共享实体放共享/业务 api 模块（如 shared-pojo、dic-api）；应用私有实体放应用模块。

## 3.3 数据访问规范

### 3.3.1 查询：优先 QueryEngine（自研 sql 框架）

```java
/* 单条查询 */
SystemDataDicEntity entity = QueryEngine.getEntityQueryWrapper(dicEntity)
    .query().where()
    .equal(SystemDataDicEntity::getDataDicCode, code)
    .pour().fetchOne();

/* 列表 + 排序过滤 */
List<SystemDataDicItemEntity> items = QueryEngine.getEntityQueryWrapper(dicItemEntity)
    .query().where()
    .equal(SystemDataDicItemEntity::getDicCode, dicCode)
    .pour().fetch();
```

1. 条件查询优先用链式 wrapper（`equal/leftLike/in/greaterEqual...` + `pour()` 结束条件段 + `fetch()/fetchOne()`）。
2. 复用型查询场景可定义 Query 类（继承 `ClassBaseQueryCriteria<T>`，字段标注 `@QueryMapping` + `@QueryField`），参照 sql 模块 README。
3. 复杂 JOIN 查询用 `@SelectSQL` 定义专用查询模型。
4. 分页统一走框架 `getPageSupport()` / `PageUtil`，禁止手写 limit 拼接。
5. **禁止**字符串拼接 SQL；禁止绕过框架直接 new JdbcTemplate。

### 3.3.2 Mapper

- MyBatis Mapper 接口放业务 api 模块 `mapper/` 包（如 `DataDicMapper`），供服务实现注入。
- 基础增删改用 Mapper 的 `insert/updateByPrimaryKey/selectByPrimaryKey`；复杂条件查询走 QueryEngine。

## 3.4 Service 规范

### 3.4.1 服务模板体系

标准 CRUD 业务继承 shared-api 模板，按删除策略选择：

| 模板 | 场景 |
|------|------|
| `AbstractLogicDeleteFullFeatureServiceTemplate` | 逻辑删除的完整 CRUD（默认首选） |
| `AbstractPhysicDeleteFullFeatureServiceTemplate` | 物理删除场景 |
| `AbstractTreeStructService` | 树形结构业务（配合 tree-struct） |
| `AbstractAuditService` | 需要操作审计 |
| `AbstractService` | 非 CRUD 的通用基类 |

模板要求实现 `getMapper()` 与 `newEntity()`；继承后仅覆写需要定制的方法。

### 3.4.2 断言与异常（强制）

所有业务校验使用 `AssertUtil` 链式断言，**这是本项目最高频的规范点**：

```java
AssertUtil.isTrue(StrUtil.isEmpty(dic.getDataDicCode()))
    .i18n("dic.code.empty")
    .errorLevel(ErrorLevelEnum.USER_INPUT_ERROR)
    .throwIt();

AssertUtil.isTrue(old == null)
    .i18n("dic.not.exists")
    .params(dicCode)
    .errorLevel(ErrorLevelEnum.USER_INPUT_ERROR)
    .throwIt();

AssertUtil.isTrue(item != null)
    .i18n("dic.has.undeleted.items")
    .params(dicCode)
    .errorLevel(ErrorLevelEnum.BUSINESS_LOGIC_ERROR)
    .throwIt();
```

规则：

1. 格式：`AssertUtil.{断言方法}(条件).i18n("资源key").params(占位参数...).errorLevel(级别).throwIt()`。
2. **必须** `.i18n(key)`，**禁止** `.message(...)`、禁止 `.message(I18nUtil.get(key))` 组合。
3. key 必须已存在于对应模块 `messages-{module}.properties`（中英文两份都要加）。
4. 错误级别语义：`USER_INPUT_ERROR`（入参问题）/ `BUSINESS_LOGIC_ERROR`(业务规则冲突) / `SYSTEM_ERROR` / `CRITICAL_SYSTEM_ERROR`。
5. 禁止直接 `throw new FormattedRuntimeException(...)`、`throw new RuntimeException(...)`。
6. 捕获系统异常需包装时用 `ExceptionUtil.newException(e, ...)`。

### 3.4.3 缓存

- 读多写少数据用 Spring Cache 注解：`@Cacheable(cacheNames = "data_dic", key = "#code")`。
- 写操作同步失效：`@CacheEvict`，可带 `condition` 防空指针。
- cacheNames 用蛇形小写下划线（如 `data_dic`）；key 用 SpEL 引用参数。
- 缓存管理器已全局配置为 Redisson（`RedissonSpringCacheManager`），模块内不得自建。

### 3.4.4 事务

- 写操作多步持久化加 `@Transactional(rollbackFor = Exception.class)`。
- 事务方法内禁止调用远程 RPC/MQ 发送等不可回滚操作；必须时先落库后异步。

## 3.5 Dubbo 服务规范

跨服务调用统一 Dubbo（**禁止**自建 HTTP 调用替代）：

```java
/* 服务提供方（dic-service） */
@DubboService
public class DataDicServiceImpl implements IDataDicService { ... }

/* 服务消费方（app） */
@DubboReference(lazy = true)
private IDataDicService dataDicService;
```

规则：

1. 服务接口定义在 api 模块（如 `dic-api` 的 `IDataDicService`），接口方法参数/返回值必须可序列化（实体、Model、基本类型、集合）。
2. 消费端引用加 `lazy = true`，避免启动时强依赖提供方。
3. 服务实现内同样遵守 3.4 断言规范；异常会随 RPC 传播，消息已经 i18n 化可直接展示。
4. 远程用户/公司信息查询走 system-api 的 `IUserRemoteService`/`ICompanyRemoteService` 等既有接口，不重复造轮子。

## 3.6 Form / VO / Model 规范

| 类型 | 命名 | 位置 | 要求 |
|------|------|------|------|
| 入参表单 | `{Biz}Form`、`{Biz}SearchForm`、`{Biz}SaveForm` | app 模块 `form/` 包（或 system-api 跨服务表单） | 实现 `Serializable` + `serialVersionUID`；`@Data`；每个字段 `@Schema(description = ...)` 必填项标 `requiredMode = REQUIRED` |
| 出参视图 | `{Biz}VO` | `vo/` 包 | 面向展示裁剪字段，禁止直接外泄实体敏感字段（密码、token） |
| 服务模型 | `{Biz}Model` | 业务 api 模块 `model/` 包 | Dubbo 跨服务传输载体，实现 `Serializable` |

Form 示例：

```java
/**
 * 数据字典保存表单
 *
 * @author abstergo
 * @since 1.0.0
 */
@Data
@Schema(description = "数据字典保存表单")
public class DicSaveForm implements Serializable {
    private static final long serialVersionUID = 1L;

    /**
     * 字典编码
     */
    @Schema(description = "字典编码", requiredMode = Schema.RequiredMode.REQUIRED)
    private String dicCode;
}
```

## 3.7 枚举规范

```java
public enum DataDicFlagEnum implements BaseEnum<Integer> {
    ENABLE(1, "启用"),
    DISABLE(0, "禁用"),
    DELETE(-1, "删除");
    // code + value 字段与 getCode/getValue
}
```

1. 业务枚举一律实现 `BaseEnum<T>`。
2. 状态类枚举命名 `{Biz}FlagEnum`；比较结果类 `{Biz}CompareEnum`。
3. 数据库存 code（Integer），展示用 value（value 如需用户可见须走 i18n）。
4. 转换用 `EnumUtil.getByCode/getByValue`，禁止手写 for 遍历。

## 3.8 新功能开发标准流程

以"新增一个业务管理功能"为例的完整步骤：

1. **建模**：设计表结构 → 实体（api/shared-pojo 模块）+ FlagEnum + 索引声明；SQL 脚本更新到 `etc/sql_file/`。
2. **Mapper**：api 模块新增 Mapper 接口。
3. **服务**：定义 `I{Biz}Service` 接口（api 模块）→ 实现类继承服务模板，业务校验全部用 AssertUtil + i18n key。
4. **i18n**：新增的 key 同步写入模块 `messages-{module}.properties` 中英文文件。
5. **控制器**：app 模块 `controller/privates` 新增 Controller（见 04 分册）。
6. **Dubbo**（如独立服务）：提供方 `@DubboService`，消费方 `@DubboReference(lazy = true)`。
7. **前端对接**：按 04/05 分册完成接口联调与页面开发。
8. **自检**：对照 07 检查清单逐项核查。
