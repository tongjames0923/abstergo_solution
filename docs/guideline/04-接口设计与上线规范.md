# 04 - 接口设计与上线规范

> 适用范围：所有对外 HTTP 接口的设计、文档化、权限控制与前后端对接上线流程。

## 4.1 URL 与接口分区（强制）

| 前缀 | 认证要求 | 控制器包位置 | 典型用途 |
|------|----------|--------------|----------|
| `/public/**` | 免认证（permit-all） | `controller/publics` | 登录、网关版本、公共查询 |
| `/private/**` | 必须认证（secured） | `controller/privates` | 所有业务接口 |
| `/private/admin/**` | 认证 + 管理权限 | `controller/privates`（`Admin{Biz}Controller`） | 后台管理操作 |

规则：

1. `@RequestMapping` 路径与包位置必须一致：`private/admin/dic`、`public/user` 等。
2. 路径用小写单词或驼峰动宾短语，操作型接口用动词命名（`query`、`saveDic`、`enableDic`、`deleteDicItem`），资源型用名词。
3. 一律 `@PostMapping` + `@RequestBody` 承载复杂参数；简单幂等查询/状态切换可用 `@GetMapping` + 路径变量。
4. 分页参数固定 `pageNum` / `pageSize`（query 参数传递）。

## 4.2 控制器编写模板（强制）

```java
/**
 * 数据字典管理控制器
 * <p>
 * 该控制器用于管理系统数据字典，提供字典和字典项的查询、新增、启用、禁用、删除等操作
 * </p>
 *
 * @author abstergo
 * @since 1.0.0
 */
@RestController
@RequestMapping("private/admin/dic")
@Tag(name = "数据字典管理接口", description = "数据字典管理相关操作接口")
public class SystemDataDicController extends BaseController {

    /**
     * 数据字典服务
     */
    @DubboReference(lazy = true)
    private IDataDicService dataDicService;

    /**
     * 启用数据字典
     *
     * @param form 包含字典编码的查询表单
     * @return 操作结果
     */
    @PostMapping("enableDic")
    @AjaxResponseType(void.class)
    @Operation(summary = "启用数据字典", description = "根据字典编码启用对应的数据字典")
    @ApiResponse(responseCode = "200", description = "成功启用数据字典",
        content = @Content(mediaType = "application/json",
            schema = @Schema(implementation = AjaxResult.class)))
    @PreAuthorize("@preAuthUtils.accountActived")
    public AjaxResult enableDic(@Parameter(name = "form", description = "字典编码信息",
        required = true) @RequestBody @NotNull DicSearchForm form) {
        dataDicService.enableDataDic(form.getDicCode());
        return successResult(null);
    }

    @Override
    public String getBusinessName() {
        return "数据字典服务";
    }
}
```

强制要点：

1. 继承 `BaseController` 并覆写 `getBusinessName()`（返回业务名称，用于操作日志）。
2. 注解组合缺一不可：`@Operation`（summary+description）、`@ApiResponse`、`@AjaxResponseType`（声明 data 的实际类型）、`@Parameter`（入参描述）。
3. 返回一律 `successResult(data)` / `errorResult(...)`，禁止手工 new AjaxResult 或返回裸对象。
4. Controller 内只做参数兜底（如 null 赋默认空串）与 Form→Entity 组装；**校验下沉 Service**。
5. 标准 CRUD 场景继承 system-api 的 `AbstractCrudController`，避免重复编写。

## 4.3 统一响应与错误码（强制）

响应结构固定为 `AjaxResult`：

```json
{ "code": 200, "message": "操作成功", "data": {} }
```

全局错误码语义（前后端共同遵守，禁止挪用）：

| code | 语义 | 前端行为 |
|------|------|----------|
| 200 | 成功 | 正常处理；如携带 message+type 自动 Message 提示 |
| 401 | 未授权 | 提示 |
| 403 | 无权限 | 提示 |
| 405 | 会话失效需重新登录 | 弹窗确认后清 token 重新登录 |
| 468 | Token 需刷新 | 自动刷新并重放请求（request.js 已实现队列） |
| 500 | 系统异常 | 错误提示 |
| 601 | 调试信息 | console 输出 |
| 701 | 通知信息 | Notification 展示 |

规则：

1. 新增错误码必须同步更新：后端 AjaxResult 定义、前端 `settings.js` 码表、本表。
2. 业务校验失败经 AssertUtil 抛出，由全局异常处理转 AjaxResult（message 已 i18n），前端直接展示 `res.message`。
3. 支持响应携带 `redirect` 字段由前端自动跳转（特殊场景使用）。

## 4.4 权限控制（强制）

1. 私有接口必须声明权限：`@PreAuthorize("@preAuthUtils.accountActived")`（账户激活态校验）为最低要求；管理操作按需要使用 `superAdmin`、`developer` 等 PreAuth Bean。
2. 权限表达式统一走 `@preAuthUtils.*` 注册的 Bean 方法，禁止在注解里写裸 SpEL 复杂表达式。
3. 数据权限由 `DataPermissionIntercepter` 统一拦截，业务代码不得自行拼接租户/公司过滤条件。
4. 新增权限点（菜单/API/数据三类，type=1/2/3）需在权限管理功能中登记；前端菜单过滤只认 type=1。

## 4.5 API 文档（强制）

1. 每个 Controller 类 `@Tag`；每个方法 `@Operation` + `@ApiResponse`；每个入参 `@Parameter`。
2. Form/VO 字段 `@Schema(description = ...)`，必填字段 `requiredMode = REQUIRED`，尽量给 `example`。
3. 泛型列表返回用 `@AjaxResponseType(value = List.class, genericArgs = {DicModel.class})` 保证文档类型正确。
4. 生产环境关闭文档：`tbs.knife4j.enable: false`。
5. 接口变更后必须在 Knife4j（http://localhost:8080/doc.html）自检渲染结果。

## 4.6 接口安全基线

1. 敏感字段（密码、token）禁止出现在 VO/Form 出参；密码类入参使用 `@PasswordValid`，用户名用 `@UserNameValid`。
2. 文件/URL 类参数必须做白名单或格式校验。
3. 幂等：重复提交有副作用的接口需服务端防重（结合 token/唯一键）。
4. 日志：敏感数据不落日志；操作日志由 `SystemOperateInterceptor` 自动记录，不需手写。

## 4.7 前后端对接与上线流程

```
1. 后端定义接口 → Form/VO + OpenAPI 注解齐全，Knife4j 自检
2. 接口契约同步 → 以 Knife4j 文档为准，向前端提供：URL、method、入参结构、出参结构、错误码
3. 前端开发     → src/api/{biz}.js 封装调用（见 05 分册），Mock 联调
4. 联调         → 本地 dev 代理 /api → 后端 8080；验证成功码与错误分支
5. 权限登记     → 新接口在权限管理登记 API 权限（type=3），菜单项登记（type=1）
6. 构建         → Jenkins 流水线（见 06 分册）：后端 jar 归档、前端 dist
7. 部署         → 后端 jar 部署；前端 dist 经 Nginx 部署并配置 /api 反代
8. 验证         → 生产健康检查 + 冒烟测试 + 文档开关确认
```

接口变更管理：

- **禁止破坏性变更**（改字段名、改语义）直接上线；需新增字段保持向后兼容，或前后端同版本发布。
- 网关版本标识通过 `app.gateway.version`（Maven 版本号注入）对外暴露（`/public/gateway/version`），前端可据此判断兼容性。
